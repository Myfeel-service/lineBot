# 右下角小幫手 agent 體驗評估與優化方向(2026-08-06)

範圍:`TutorialAgent.vue` + `useWorkspaceAlerts` + `useSetupStatus` + `useDailyBrief` + `/api/admin/alerts` + 問助理(`ai-admin-agent.ts`)。
起因:老闆問「狀態是否太多會誤導使用者」+ 期待 agent 成為「全站異常告知/提醒/建議」的單一入口。

---

## 一、結論先講

1. **狀態機的「紀律」是對的,問題不在邏輯層,在呈現層的同屏堆疊。**
   紅=影響客人/橘=建議處理/藍=可以更好/查不到≠沒事/失敗要現形——這幾條線都守得很好,不建議動。
   但「目前狀況」分頁最壞情況會同時堆 **13 個區塊**、出現 **3 顆以上「重新檢查」按鈕**,灰色誠實橫幅最多 5 條各講各的——這才是「太多狀態」的體感來源。
2. **「一切正常」目前只代表「13 種訊號正常」,不是「整個網站正常」。**
   盤點過的 31 種持續性異常只收了 13 種(42%),LINE webhook 連自動檢查都沒有。要讓 agent 擔起「全站告知」的承諾,覆蓋率是最大的洞,不是 UI。
3. **主動性只到「你有開後台才看得到」。**
   實測抓到過「客人等真人 53 小時、通知又是關的」——如果那幾天沒人開後台,這套再漂亮也是零。c 層(LINE 推播)是下一個質變點,老闆先前拍板 a+b 先做、c 未做。

## 二、現況狀態盤點(使用者看得到的)

| 部位 | 狀態數 | 明細 |
|---|---|---|
| FAB 按鈕 | 4 | 平常/紅點+光暈(critical)/中性數字+光暈(純設定缺)/開啟 |
| 主動氣泡 | 2 | 異常氣泡(critical,每組合一次)/新手氣泡(一次性) |
| verdict 狀態列 | 5 | 紅/橘/藍(差 N 項上線)/綠(一切正常)/灰(檢查不到) |
| 異常區 | 4 | 現在影響客人/建議處理/可以更好/沒有發現異常 |
| 誠實現形橫幅 | 5 | 首查失敗/這次失敗(舊結果)/N 項查不到(異常)/已靜音 N 項/N 項查不到(設定) |
| 開場白 agentLine | ~9 分支 | 依壞了→沒做→日報→建議的優先序 |
| 設定體檢區 | 3 | 進度條+待辦/全完成閉環/缺項巡覽 |
| 閉環回報 | 3 | 導覽完成/修好了/還沒好 |
| 日報 | 3 | 有對話格子/沒對話/unhandled 警語 |

合計約 **38 種可分辨狀態**。單獨看每一種都有存在理由;誤導風險出在**同屏組合**與**用語重複**(「建議處理」既是橘組標題又出現在 verdict 文案,與藍組「可以更好」的「建議」一詞相鄰)。

### 真的可能誤導的 4 個點(P0)

1. **紅點數字 ≠ 面板頭條數字。**
   FAB 數字 = critical + 必要設定缺項(`badgeCount`),但 verdict 只講 critical:「FAB 顯示 3 → 打開卻說 1 件事正在影響客人」。開場白有補講,但最顯眼的兩個數字對不上,正是老闆會抓的 drift。
   → 修法:兩者都有時 verdict 併句「1 件事正在影響客人、另差 2 項必要設定」。
2. **灰色橫幅最多 5 條同時出現,各配一顆按鈕。**
   首查失敗/舊結果/查不到 N 項(異常)/查不到 N 項(設定)/已靜音 N 項——語氣格式各異、加上進度條的「重新檢查」共 3+ 顆同功能按鈕。
   → 修法:收斂成**一條「檢查健康度」列**(例:「這次有 3 項檢查不到、已靜音 2 項 · 重新檢查」),點開才展開明細。靜音那條可留在異常區尾。
3. **「一切正常」超賣。**
   涵蓋率 42% 時說「一切正常」,等於替沒檢查的 18 種背書。
   → 短期修法:verdict 或 freshness 帶透明度「檢查了 13 項常見問題,沒有發現異常」;長期靠補覆蓋率。
4. **三個聲音同時說話。**
   postTourNote + postFixNote + agent 開場白是三個獨立區塊,都在「代替 agent 講話」。
   → 修法:併入同一顆 agent 泡泡(閉環回報應該就是開場白的第一句),一個 agent 一個聲音。

### 看過但「不建議動」的(防守清單)

- 只有 critical 進紅點、warning 不進——**守住**,這是紅點還有意義的原因。
- critical 不可靜音、warning 靜音 7 天且現形——**守住**。
- 查不到=unknown 單獨講、不歸類——**守住**,這比合併成「正常」誠實得多。
- 換工作區先 reset 再查——**守住**(A 家扣款失敗掛在 B 家是事故)。

### 順手的小毛病

- `TutorialAgent.vue` 文案殘留:`必要設定都完成了 可以上線囉!`缺逗號、「點下面就能開始 」「看起來修好了 」句尾空白(疑似 emoji 移除殘跡),共 3 處。
- llmError、claimPushUnmarked 是「系統側問題,使用者其實修不了」,卻與可動手項混排同一視覺。建議加一個小標記「這是系統端狀況,你不用操作」——不然使用者點進去繞一圈發現無事可做,會侵蝕「點了就能修」的信任。

## 三、優化方向(依老闆的期待:告知全站異常 → 提醒 → 建議)

### 方向 A:呈現層收斂(小工,先做)
上面 P0 四項 + 文案毛病。**不新增任何狀態,只合併。**
> ✅ 2026-08-06 已完成(未 commit):verdict 併講必要缺項、灰橫幅收斂成一條 checkGapLines、閉環回應併入 agent 泡泡(.ta-note 退役)、文案殘跡 4 處(比報告多抓到 1 處)。typecheck 0 錯、867 測試綠。

### 方向 B:覆蓋率——「告知整個網站」的地基(中工,最重要)
- **LINE webhook 常駐檢查**:目前只有按按鈕才驗。webhook 掛掉=整個機器人裝死,是所有異常裡最致命、卻唯一沒自動檢查的。建議進 probe(檢查 LINE 平台上 webhook URL 與啟用狀態,或看「最近 N 小時是否收過事件 vs 好友有互動」訊號)。
  > ✅ 2026-08-06 已完成(未 commit):新異常 `lineWebhookBroken`(critical,admin 可見),probe 打 LINE GET webhook endpoint(不打 test API,留額度給設定頁手動驗證),抓四種壞法:沒設定/被停用/網址指向別的系統/權杖失效(401);外部查詢 5 分鐘快取;正規化比對函式與 line-webhook-verify 共用同一支。不需要新 Firestore 索引。
  > ⚠️ 同日修一個實測誤報:第一版「網址比對」拿**使用者當下瀏覽的 origin** 當基準,本機開發/雙網域開 myfeel 後台就被誤判「指向別的系統」。修正=改比 `PUBLIC_BASE_URL`(runtime config appBaseUrl,對外正式網址的單一來源);沒設定或設成 localhost 就跳過比對(寧可漏抓不誤報);detail 直接寫出 LINE 後台填的網址。另補落地閉環:卡片 CTA 帶 `?verify=webhook`,進組織設定頁自動捲到「檢查連線」並實跑一次測試,不讓使用者在長頁面裡自己找要修什麼。
  > ⚠️ 再修一輪(同日,myfeel 實測第二回):LINE 真的還填著舊網域 `bot.myfeel-tw.com/webhook`,但舊網域 DNS 仍指向同一套 app、訊息照常進來(昨日 25 場)——紅牌「機器人收不到客人訊息」與事實不符,會教人不信任紅牌。修正=**拆成兩顆**:`lineWebhookBroken`(critical)只留「確定收不到」三種(沒設定/停用/權杖失效);新 `lineWebhookUrlMismatch`(warning)講「網址不一致,目前可能還通,但舊網址一失效就無聲斷線」。一次 LINE 查詢兩顆共用。**myfeel 待辦:把 LINE Developers 的 Webhook URL 換成正式網址(lineminime.com/webhook),或確認 PUBLIC_BASE_URL 應該是哪個網域。**
  > 🔁 同日 code review 後補四修(未 commit,typecheck 0、876 測試綠):
  > 1. **誤報只修了一半**:probe 換基準了,但它導去的組織設定頁還在拿 `window.location.origin` 當 `compareUrl`,雙網域下同一個誤報照長出來——而且 `webhookStatusBadge` 把「網址不一致」排在「測試成功」前面,會蓋掉「✓ 一切正常」,連「複製貼到 LINE」那格也會叫人把錯的網址貼去覆蓋。修法=`line-workspace` GET 回傳 `publicBaseUrl`(appBaseUrl,server-only 不進 public config),頁面的 webhook/LIFF 建議網址與 `compareUrl` 全部改吃它,後端沒設定才退回瀏覽網址。前後端從此同一把尺。
  > 2. **CTA 在自己那頁按了沒反應**:handoff 只寫在 `onMounted`,但 Nuxt 預設 page key 不含 query;小幫手在組織設定頁本身也掛著,在該頁點卡片只有 query 變→元件不重掛→onMounted 不跑→不捲動也不測試。修法=改成 `watch(() => route.query.verify)`。
  > 3. **`?verify=webhook` 沒清掉**:留在網址上=每次重整/上一頁回來都再真的請 LINE 送一則測試訊息(有次數上限,probe 刻意不打就是為了留額度)。修法=消費完 `router.replace` 拿掉參數(query-only 導航不會觸發 `onBeforeRouteLeave`,不會誤跳未儲存確認)。
  > 4. **「剛剛去修的好了沒」永遠說還沒好**:`refreshAll(true)` 的 force 只跳過前端 60 秒節流,後端那層 5 分鐘外部查詢快取沒有 bypass;人剛在 LINE 後台改完回頭問,最多五分鐘一直被回「還沒解決」,而正式環境多台各存一份還會一次說好一次說壞。修法=force 一路傳到底(`/api/admin/alerts?force=1` → `collectWorkspaceAlerts({ skipCache })` → webhook probe 跳過讀快取、仍寫入)。只有換工作區、按「重新檢查」、以及 30 分鐘內有待驗證修復這三種情境會 force,平常開面板照樣吃快取。

## 五、產品層評估:「核心=agent+AI」目前做到了嗎?(2026-08-06 補)

一句話:**工程深度做到了、商業模式綁上了;但對客人還沒兌現(正式環境 AI 仍關),對操作者做到一半(agent 會講話、不會動手)。**

### 5.1 做到的部分(證據)

- **AI 織進了訊息管線,不只是保底。** `handler.ts` 的順序=敏感情境安全層 → 自動回覆規則 → 腳本 → AI 保底;但「走哪條腳本 vs 交給 AI」本身就是一次 LLM 統一意圖路由(`ai-answer.ts`),關鍵字只是快速通道。路由層已經是 AI。
- **能力面完整**:RAG 知識庫(來源→切卡→embedding→檢索)、反問澄清、轉真人+值班通知+勿擾、對話級產品鎖、圖片辨識 Phase1+2、試答 playground、學習迴圈(建議收件匣:聚類→草稿→試答驗證→自動銷案)。
- **品質治理是「核心產品」等級**:四輪以上稽核(06-23 實測、07-02 四路審查、07-31 live 48 場景、08-05 跨產品)、口徑文件、aiUsage 遙測、成本盤點(每則≈NT$0.11)。一般外掛功能不會有這種待遇——投資強度本身就是「把 AI 當核心」的證據。
- **程式量佐證**:server/utils 84 支裡 23 支是 ai-*(約 8,900 行),加上 3,700 行的 handler 深度耦合 AI 流程。
- **商業模式已綁死 AI**:計費賣「則數」,唯一 enforce 的額度就是 answeredQuota——收的錢就是 AI 回覆的錢。

### 5.2 沒做到的部分(依嚴重度)

1. **核心未兌現:正式租戶的 AI 是關的。**(至 07-27 遷移備忘;go-live 三個洞:draft 期排班、腳本沒搬、成功標準未定。)今天客人實際感受到的仍是傳統關鍵字 bot。所有已建能力的價值在客人端都乘以 0,這是唯一真正的「沒做到」。
2. **後台 agent 止於唯讀+被動。** 問助理 7 個工具全唯讀,「幫我把那條規則停掉」還是要自己去頁面點;主動性只到「開後台才看得到」(第三節 C);異常覆蓋率 42%(第三節 B)。agent 的「告知/教學/查詢」形有了,「代辦」沒有。
3. **結構性張力:舊 bot 機制能整個遮蔽 AI。** anyText 規則攔截=AI 等於沒開(07-31 稽核 P0,現已有 alert 盯著)。管線「確定性優先、AI 保底」是對的設計,但衝突只在事後由小幫手報警,不在儲存規則的當下擋。

### 5.3 對「核心=agent+AI」的優化方向(策略層)

- **S1 上線是唯一的第一優先**:補 go-live 三個洞(draft 期排班、腳本搬遷、成功標準),讓正式租戶的 AI 開起來。上不了線,其餘都是內部練習。
- **S2 後台 agent 從「查」到「做」**:問助理接 tool-call(低風險動作先行:停用規則/重新同步來源/採用建議草稿,附確認步驟);權限沿用既有收斂(內容 agent/設定 admin)。腳本引擎的動作累積器已是現成底座。
- **S3 衝突就地攔**:儲存 anyText 規則且 AI 開著時,當場講「這會擋住 AI」,不等右下角事後報警。
- **S4 讓學習迴圈上線**(commit+部署建議收件匣):「用越久答越好」是 agent 產品的護城河,也是「AI 是核心」最有力的長期證據。

## 七、新帳號嚴重性呈現（2026-08-07 老闆回饋修正）

**問題**：剛加入、幾乎沒填東西的帳號（例：小胖商店，必要 0/2＋加分 0/3），小幫手打開來整片綠、還說「目前沒有發現異常」——看起來沒什麼大問題，但實況是機器人完全不會動。根因三個，全在呈現層：

1. 「還沒上線」被當「進度」用品牌綠講（結論卡 ℹ️「差 2 項必要設定**就能上線**」＝好消息長相）。
2. 「必要」標籤綠底白字，掛在**還沒做**的項目上長得像「已完成」徽章。
3. 「目前沒有發現異常。」對還沒開通的帳號照樣顯示——異常檢查全部撲空（本來就沒接東西），安心話蓋掉重點。

**拍板原則（第二輪，2026-08-07 老闆定案）**：講後果、不講進度；**「還沒上線」本身就是大問題＝紅級**（取代第一輪暫定的橘），且排在「建議處理」級異常之前——沒開通的帳號不能被一顆橘色警告把頭條搶走。紅的語意從「客人正在受影響」擴為「客人正在受影響，或帳號還不能上線」。

已改（TutorialAgent.vue + _tutorial-agent.scss）：
- 結論卡「還不能上線：<後果>（差 N 項必要設定）」用 `danger` 紅級，分支順序＝critical 異常 → 還不能上線 → warning 異常。後果依缺的根結講：LINE 沒接＝「客人傳訊息進來，不會有任何回應」；LINE 有接但 AI 沒開＝「客人的訊息進得來，但 AI 不會回」。
- 「目前沒有發現異常」只在必要設定全完成後才顯示。
- 開場白同樣後果先行；另外「AI 開著＋知識庫全空」單獨點名（客人問什麼 AI 都答不出來、幾乎都轉真人），但不擋「可以上線」（知識庫仍是拍板過的加分項）。
- FAB 數字徽章一律紅（`--calm` 分色退役；灰、橘都會被讀成「不急」）。

**未上線狀態的版面重整（同輪 UI/UX 優化）**：
- 必要缺項改成「開通步驟」區塊：標題「先做這 N 件，機器人才會動」＋①②編號（依賴順序：先接 LINE 才輪得到 AI 開關）、橘左條＋橘號碼圈；加分項獨立區塊、標題「加分項（做了 AI 更好用，不做也能上線）」。
- 卡上的「必要/加分」小標籤退役（分組標題講一次就夠；⛔別復活成品牌綠標籤——像已完成徽章）。
- 「帶我看一遍還沒做的」從主 CTA 旁移到清單後面當次要出口（與「用聊天引導完成開通」並排會互搶）。
- 進度列加分項只報數（N/M），定位說明由區塊標題講，同一句話不講兩遍。
- 色彩階梯：紅＝結論卡（還不能上線）與異常、橘＝要做的步驟、中性＝加分項——面板內全紅的話紅就沒有意義。
