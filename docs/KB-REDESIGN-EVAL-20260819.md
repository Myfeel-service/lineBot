# 知識庫修法路線評估：哪些用「修」就好、哪些「換個做法」更划算

> 2026-08-19，接在同日健檢報告（`KB-PIPELINE-AUDIT-20260819.md`）之後。
> 問題清單與證據看健檢報告；這份只回答一個問題：**每一群問題,是打補丁划算,還是換一種做法划算？**
> 待辦狀態一律看 `STATUS.md`；這份寫完凍結。

## 評估原則（先講清楚怎麼判斷,結論才可檢驗）

1. 「換做法」要能**一次蓋掉一整類問題**（含未來還沒犯的）才值得;只解決眼前那一條的重做是浪費。
2. 規模未到就不預先重構——現在兩個租戶,來源總數離任何天花板都還很遠。
3. 任何資料結構/基礎設施變更,成本自動 ×2（兩個 Firebase 專案各跑一次）,一人團隊的維運面每加一種機制都是長期負債。
4. 已驗證是對的設計（指紋六態、自動套用守門、job 每步落地）不動。

## 總結論

| 問題群 | 路線 | 一句話理由 |
|---|---|---|
| 停用卡復活（C-41） | **修**（單點守門） | 所有寫入都過同一個函式,一行守門堵四條路 |
| 誤刪防線（C-42） | **換做法：回收桶**＋防呆照做 | 軟刪除一次蓋掉健檢裡五種「資料無聲消失」 |
| 套用重複/指紋吞變動（C-43/C-44） | **修** | 冪等鍵與條件推進都是小改,機制本身方向沒錯 |
| 燒錢無上限（C-45） | **換做法：收口在 gemini.ts 單一出口** | 成本跟逐入口補差不多,保護面大一截且蓋未來 |
| 匯入 job 韌性（C-46） | **修**,不換基礎設施 | 真佇列的邊際效益低,維運負債高 |
| 排程規模（C-48） | **修,且不急** | 規模未到,是上量前要還的債不是火警 |
| 重複卡/同步比對（C-40） | **修＋一個零程式的治本**;大重構列觸發條件 | 痛點集中在輪播列表頁一種來源 |

## 逐項評估

### 1. 停用卡復活（C-41）→ 修就夠

**修**：`runIndexOnChunk` 加「既有狀態是 disabled 就維持 disabled」一條規則（四條復活路全過這個函式）;到期排程對 failed 卡補寫 disabled;tag 檢索補 activeUntil 過濾。**0.5〜1 天**。

**曾考慮的重做**：status 欄位其實混了兩件事——「索引到哪了」（pending/indexed/failed）和「店家要不要用它」（disabled）。拆成兩欄（`indexState` + `enabled`）是資料模型的正確答案,這一類 bug 從此不可能發生。但要回填既有卡、改所有查詢、補複合索引,×2 租戶,約 **2〜3 天**。

**判斷**：先修。單點守門已把已知路徑全堵住;**若之後又冒出第五條復活路,那就是拆欄的訊號**,屆時再做。

### 2. 誤刪防線（C-42）→ 換做法:知識卡回收桶（推薦本次評估裡效益最大的一項）

**修**（照健檢建議）：gsheet 刪除比例 >30% 不刪改標待確認、單分頁空讀當異常、gid 掉了直接 fail。**1 天**。這些仍然要做,是第一道防線。

**換做法**：所有「刪知識卡」（gsheet 同步刪、resync 的 delete_old、單卡刪、刪來源連坐）一律改成**軟刪除**——進回收桶（掛 `purgeAfter`,30 天後排程真刪）,UI 給「還原」。disabled 狀態機制、排程、體檢清單全是現成的,估 **1.5〜2 天**。

**為什麼值得**：健檢裡至少五個獨立情境的結局都是「卡片無聲消失且救不回」——gsheet 誤刪列、多分頁空讀、gid 掉頁、resync 誤選刪除、兩人併發互踩。逐路補防呆是打地鼠,回收桶把整類後果從「P0 災難」降級成「可還原的小事」,**未來任何新的刪除路徑自動受保護**。這正是「換做法蓋掉一整類」的典型。

**判斷**：防呆＋回收桶都做,回收桶的優先級高於長尾防呆。

### 3. 套用重複與指紋吞變動（C-43/C-44）→ 修

診斷（diff 出給人審）這個產品方向是對的,問題全在套用端的工程細節:冪等鍵、errors>0 不記成功、keep_old 不推進指紋、gsheet 補 appliedContentHash 與「N 張已鎖定」可見性。沒有哪種重做能便宜地取代這些——它們本來就是缺的螺絲,不是錯的機器。**1〜2 天**（與 C-40 的配對改法同一片程式碼,一起動）。

### 4. 燒錢無上限（C-45）→ 換做法:額度收口在 LLM 單一出口

**已查證的前提**：全系統 LLM 與 embedding 呼叫 100% 走 `server/utils/gemini.ts`（generateText/generateParts/generateJson/embedDocument/embedQuery,7 個消費模組全從它 import）。

**做法**：gemini.ts 各函式收選填的 `{workspaceId, purpose}`——有帶就查當月 import＋embedding 桶對上限,超額丟 429;沒帶先 log 警告讓漏網呼叫點現形,分批補上。入口端（建 job、bulk-create）另做一次前置檢查,讓使用者在**開始前**就看到「額度不足」而不是跑一半死。**1〜2 天**。

**對照純修**（逐入口加檢查）：一樣要動七八個檔案,但只保護已知的九條路;之後每加一個新功能都要記得補,而「忘了補」正是這次健檢抓到的病。收口版成本差不多、保護面大一截,還讓「額度」第一次變成全系統的不變式——**明顯划算**。

附帶照修：自動套用「先付錢再判斷」→ 來源記連續退人工次數,連 3 次跳過 LLM 直接標有變動。

### 5. 匯入 job 韌性（C-46）→ 修,明確不換基礎設施

**換做法選項**：SQS／Cloud Tasks 真背景 worker,job 不再靠瀏覽器輪詢推進。
**否決理由**：全案排程已收斂在「Cloud Scheduler 打 HTTP」單一模式（Amplify 不跑 scheduledTasks 踩過雷後的定調）;加一種新基礎設施＝部署面 ×2 租戶＋一人團隊多養一套東西,換到的只是背景推進的延遲——而匯入場景使用者本來就開著頁面在等,感受差異趨近零。

**修**：每步續租＋work.json 帶版本鎖＋錯誤分類（429/5xx 不落終局,連續 N 次才 error）＋jobId 當 bulk-create 冪等鍵＋DELETE 取消端點＋**cron 每輪撿「無主且未過期」的 job 推一步**——最後這條讓「背景工作」以 10 分鐘粒度名副其實,等於用現有模式拿到八成的 worker 效益。**2〜3 天**。

### 6. 排程規模（C-48）→ 修,而且誠實說:不急

現在兩租戶、來源數十個,250 筆窗離撞到還很遠——**今天沒有任何人被餓死**,它是上量前要還的債。修法（游標輪轉＋每租戶配額＋失敗退避＋truncated 回報）**1〜2 天**,排 P0 之後即可。per-task 獨立排程或佇列同第 5 條理由不做。

### 7. 重複卡與同步比對（C-40）→ 修＋零程式治本;大重構列清楚觸發條件

**修**：computeDiff 加「第 0 輪」——卡片內容裡的「連結：/projects/xxx」專案代號當穩定鍵,先按代號配對再走標題/相似度（列表頁來源從此改名不斷鏈）。與 C-43 一起動。

**零程式的治本**：輪播首頁本來就不該當知識來源。系統已會警告動態頁,再加一條「這頁長得像輪播列表→建議改用固定全品項頁或逐頁匯入」的引導;MYFEEL 這個來源直接換成列表頁網址,重複的根源就沒了。

**曾認真考慮的大重構**：卡片身分錨定原文——原文按結構分段、每段記指紋,卡片掛「來自哪一段」;重新同步只重切有變的段,沒變的段零 LLM 費、diff 變成精確比對而非啟發式配對。這是業界 RAG 管線的標準形,能同時消滅 title 漂移、假差異、白重切三類問題。**為什麼現在不做**：現行分段是「每 8000 字找換行硬切」,前面插一句話後面全部位移、快取整批失效——要先改成按結構/內容定位的分段,牽動切卡器、比對、儲存結構,還要遷移既有幾百張卡 ×2 租戶,估 **5〜8 天**;而眼前的痛集中在「輪播列表頁」單一形態,上面兩帖便宜藥就能治。**觸發條件寫死在這**:當「URL 來源數 × 重同步頻率」讓切卡 LLM 費在月帳單上有感,或固定產品頁也開始大量出現假差異時,回來做這個。

### 8. 順帶確認「不重做」的清單

- **LLM 語意切卡不放棄**：「一卡一事、人可編輯」是產品核心,機械分段是檢索工具不是產品。
- **指紋六態偵測不動**：健檢確認設計正確。
- **診斷 diff 人工審的 UX 方向不變**：自動化擴大靠自動套用守門逐步放寬,不靠重寫。

## 建議動工順序（合併兩份報告後的最終序）

1. `C-41` 復活單點守門（0.5〜1 天）——最小成本擋「客人吃到過期資料」
2. `C-42` 回收桶＋gsheet 三防呆（2〜3 天）——把所有「無聲消失」降級成可還原
3. `C-43`＋`C-40`＋`C-44` 同片程式碼一起修（1〜2 天）——套用冪等、穩定鍵配對、指紋條件推進;MYFEEL 來源同步換成列表頁網址
4. `C-45` 額度收口 gemini.ts（1〜2 天）
5. `C-46` 匯入 job 韌性（2〜3 天）
6. `C-48`＋`C-49` 長尾照清單排

P0 全清約 **7〜10 個工作天**;其中兩處改走「換做法」（回收桶、額度收口）不是為了重做而重做——它們的成本與補丁同級,但各自把一整類問題（含未來的）一次蓋掉。
