# 後台載入速度稽核（2026-08-27）

> **這是決策紀錄，寫完凍結。** 狀態一律看 `docs/STATUS.md`（本輪結論收在 `E-20`～`E-27`）。
> 給老闆看的版本：Artifact「後台為什麼要等六秒」<https://claude.ai/code/artifact/81e2a626-8289-4271-a164-4000ba0056a3>

## 一句話

骨架 1.6 秒出現、數字要等 **2.5～6.3 秒**才到齊；**17 個工作區頁面裡有 16 頁，最後在等的不是自己那一頁的資料，
是每頁都重跑、其中一半還重複跑兩次的背景檢查**。問題不在各頁寫得好不好，在那層共用外殼。

## 怎麼量的（要重驗照這個做）

三路交叉，互相對得起來：

1. **正式站端到端**（主證據）：puppeteer 打 `https://lineminime.com`，把真的 `idToken` 寫進 Firebase SDK 用的
   IndexedDB（`firebaseLocalStorageDb` / `firebase:authUser:{apiKey}:[DEFAULT]`，值含 `stsTokenManager`）→
   直接走訪 22 個後台頁面，記每支 `/api/` 的送出與回應時間。**全程唯讀（只有 GET）**。
   token 產法沿用既有招：admin SDK `createCustomToken` → identitytoolkit `signInWithCustomToken` 換 `idToken`＋`refreshToken`。
   「到齊」定義＝從導航開始到最後一支 `/api/` 回應完成（連續 1.5 秒沒有新的完成就算停）。
2. **逐支端點**（找原因）：本機 `nuxt dev`（`.env` 指正式 myfeel）暖機一次後每支量 4 次取中位數，同時記回應大小。
   ⚠️ 本機到 Firestore（nam5，美國）單趟往返實測 **270～300 毫秒**，所以本機絕對秒數比正式站悲觀，
   只用來比較各支之間的相對成本與「幾趟往返」。
3. **資料量與查詢實驗**（驗修法）：直接用 admin SDK 對正式資料跑 `count()` 與同一支查詢的
   全欄位 vs `select()` 版本對照計時。

量的帳號＝MYFEEL 正式（`212405d2-…`）：好友 4,684、對話 4,977、對話場 6,268（近 30 天 2,002／近 90 天 4,335）、
模組 63、標籤 35、知識卡 648。

## 八項發現

照「省下的秒數 ÷ 動工成本」排序。編號對應 `STATUS.md`。

1. **`E-20` 同一件事在同一次載入問兩遍。** 開通進度 17/17 頁、異常檢查 15/17 頁、方案額度 3 頁。
   根因＝`useWorkspaceAlerts.ts:502`／`useSetupStatus.ts:132` 的 `let inflight` 在 composable 函式內，
   每個呼叫端各一份；`usePlanSummary.ts` 用 `ref` 不是 `useState`。正確寫法在 `useWorkspace.ts:50`。
   ⛔ 別只加 TTL：兩個呼叫端是同時發車。
2. **`E-21` 沒人看的昨日摘要每頁先查 3 次 KPI。** 只顯示在小幫手面板打開後，卻在 `onMounted` 就抓齊。
3. **`E-22` 統計端點整包搬對話場、沒有預聚合。** 對話統計一次開頁約 6,000 筆讀取。
4. **`E-27` 權限清單是畫面級閘門。** 0.4～1.7 秒，沒回來之前該頁一支都不發。
5. **`E-24` 客服對話的分頁數字排在清單之後。** 白排 2.3 秒。
6. **`E-23` 五頁為了下拉選單下載 133 KB 完整模組內容。** 只用到 `id`／`name`／`isActive`。
7. **`E-25` 圖表庫在全站 plugin，每次首載多 182 KB。** 只有兩頁畫圖，官網訪客也在載。
8. **`E-26` 好友清單為 20 筆讀 120 筆、翻頁用 `offset`。**

### 前端包（空快取、正式站 CDN）

首次載入：JS 86 個檔共 754 KB、CSS 26 個檔共 79 KB、first-contentful-paint **1596 ms**。
其中 entry chunk 一支 324 KB（brotli）。把 `echarts.client.ts` 換成空 plugin 重新打包實測：
entry **1,010 KB → 464 KB**（gzip 341 KB → 159 KB）＝圖表庫佔 entry 一半以上。
（實驗做完已還原，`app/plugins/` 無變更。）

## 一起量到、確認沒問題的部分

- 超管頁 1.4 秒、只打 1～2 支＝這份報告的對照組。
- 有記憶體快取的端點是毫秒級（`ai/settings` 6 ms、`liff/config` 3 ms）＝快取真的有效。
- **異常檢查內部是並行的**（二十幾個探針同時跑，`workspace-alerts.ts` 刻意不 await 前置查詢）。
  它慢是因為要問外部 LINE API 加掃多個集合，不是寫法錯——所以問題是「打兩次」不是「太慢」。
- 骨架 1.6 秒就出現，不是白屏等到 6 秒。
- 背景輪詢的把關還在：分頁在背景不刷新、搜尋框有字不重抓清單（08-11 讀取費那批防線）。

## 限制

- 每頁只走一次，單一數字容許 ±0.5 秒（觀察到最大離群值：本機 `trend` 90 天有一次 22.6 秒，
  三次取樣的其餘兩次是 4.1／4.4 秒）。**但「打幾支、哪一支最後回來、哪些重複」是結構事實，不受浮動影響。**
- 正式站量的是 super admin 身分。`workspaces/my` 的 super admin 路徑會讀全部 workspaces＋organizations
  （7＋數筆，仍是兩趟並行往返）；一般 owner 走的是成員資格路徑，趟數相近但不完全相同。
- 本機數字含約 270 ms／趟的跨洋往返，不能當正式站的絕對值。
- 沒量：LIFF 前台、公開官網各頁、行動網路下的實際體感（`E-13` 後台本來就沒有手機版）。
