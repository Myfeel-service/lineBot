## P0：先修

### P0-1 停用／過期的知識卡會被系統自己「復活」，繼續對客人講話

**會發生什麼**：店家把一張募資倒數卡設了有效期限（或手動關掉「供 AI 使用」），以為它下架了。結果四條路任何一條都會把它無聲地打開：

1. 按一次「補問法」（reenrich）——它挑卡時不看停用狀態，補完問法順手把卡片重建索引成「可用」。
2. Google 試算表自動同步——比對時不看停用狀態，那列文字一改，每小時一次的同步就把卡寫回「可用」。
3. 手動對單卡按「重新索引」或改個錯字存檔——同樣不看停用狀態。
4. 最陰的一條：卡片到期當天剛好碰上 embedding 暫時失敗（狀態=failed），到期排程只搬走 `activeUntil` 不改狀態；十分鐘後同一輪 cron 的自動重試把它重試成功→寫回「可用」。此時到期欄位已經被搬走，**沒有任何機制會再下架它一次**。

另外品號（tag）命中的檢索路徑只看「狀態=可用」、不看有效期限，到期後排程處理前的空窗（最長 10 分鐘）客人拿品號問就直接命中，還給 0.95 高信心。

**為什麼嚴重**：過期募資價、下架折扣碼直接進客人對話。全案只有「自動套用」一處想清楚了這件事（明文擋 disabled），其他路徑全漏。

**建議修法**：在 `runIndexOnChunk` 統一守一條「既有狀態是 disabled 就維持 disabled」，四條路一次堵住；到期排程對 failed 卡也寫 `status:'disabled'`；tag 檢索路徑補 `activeUntil` 過濾（抽成共用 helper 跟向量路徑同一把）。

**證據**：`server/utils/ai-reenrich.ts:33-44`（select 沒取 status）＋`ai-knowledge-chunker.ts:513-525`（needsQuestionEnrichment 不看 status）；`gsheet-sync.ts:78-81,140-155`；`[chunkId]/reindex.post.ts:26-30`、`[chunkId].put.ts:42-48`；`cron-maintenance.ts:963-977`（failed 只搬欄位不改狀態，已實地抽查確認）＋`ai-knowledge-chunks.ts:332-340`（重試成功一律寫 indexed）；tag 路徑 `ai-knowledge-chunks.ts:507-521` vs 向量路徑 `:406-412`。對照組（證明是漏洞不是設計）：`reindex-all.post.ts:44` 與 `ai-knowledge-autoapply.ts:53-56` 都明文跳過 disabled。

### P0-2 Google 試算表誤刪列＝一小時內整批知識卡無聲消失

**會發生什麼**：三個情境，全都不出聲：

1. 商家在 Sheet 開了篩選誤刪 90/100 列 → 下一輪自動同步照單全刪 90 張卡。網址來源有兩層縮水防護＋強制確認，試算表路徑一層都沒有；唯一的底線是「整張表一列不剩」才擋。
2. 來源涵蓋兩個分頁，其中一頁 API 讀到空（抖動或真被清空）→ 空頁檢查只看跨分頁總和 → 該頁對應的卡全部被當「表上已不存在」刪光。
3. 商家刪掉重建了分頁（gid 變了）→ 系統找不到原分頁時**靜默改讀別的分頁** → 說明文字變知識卡、原 FAQ 卡整批被刪。

而且排程同步成功不推播（拍板過的），所以災情發生時 LINE 一句話都不會提。

**建議修法**：套用刪除前算比例，`刪除數/現有數 > 30%`（或 >10 張）就不刪、改標「有變動待確認」交人工；任一目標分頁回 0 有效列直接當讀取異常報錯；gid 有值卻找不到分頁時直接失敗並寫明原因，不要退回猜測。

**證據**：`gsheet-sync.ts:158-167`（刪除無守門）；`google-sheets.ts:298-327`（空頁 continue 在總和累加前）；`google-sheets.ts:231-237`（gid 找不到往下掉到名稱猜測）。對照：URL 路徑的 `ai-knowledge-autoapply.ts:31` 與 `preview-jobs/[jobId].get.ts:92-98` 有雙重縮水偵測。

### P0-3 重新同步的「套用」會逾時，而且按第二次就多一整批重複卡

**會發生什麼**：150 張卡的來源按「套用」→ 後端**一張一張**串行做 embedding（一張 300ms 起跳）＋最後還要跑一次總覽卡 LLM → 穩穩超過閘道 30 秒 → Lambda 其實跑完寫入了，但前端收到「套用失敗」→ 使用者再按一次 → 所有「新增」項用新的隨機 ID 再建一遍 → **知識庫多一整批重複卡**。這是 `C-40` 重複品項的另一個上游。當初 preview 就是因為同一種逾時才改成 job 機制的，apply 沒跟上。

順帶：套用過程單卡失敗只收進 errors 陣列，來源狀態照樣寫「已同步完成」——**部分失敗被記成完整成功**。

**建議修法**：apply 也改走 job（沿用現成的租約機制），或至少收 client 帶的 applyId 做一次性認領＋新增前按標題查重；`errors.length > 0` 時不推進指紋、不清除「有變動」標記。

**證據**：`resync-apply.post.ts:135-226`（序列迴圈、每筆同步 embedding）、`:176`（每次 uuidv4 無查重）、`:229-232`（之後還跑總覽 LLM）；對照 `resync-jobs.post.ts:22-26` 自述 job 機制就是為了逾時而生。

### P0-4 選「保留舊卡」會把網頁變動永久吞掉；試算表的手編卡則是永久分歧、無任何提示

**會發生什麼**：

1. 網址來源：店員手動改過的卡在 diff 裡預設「保留」。網頁後來改了價格 → 店家按「套用」（信任預設值）→ 卡片沒動，但系統把「已同步到哪一版」的指紋**無條件推進到新版**。此後卡片寫 100、網頁寫 120，再按重新同步只會得到「已是最新，無變動」，排程也永遠不再提醒。變動被永久吞掉。
2. 試算表來源更糟：手編卡每次同步都被跳過（合理），但整張表的指紋照樣前進（不合理）→ Sheet 才是商家心中的事實來源，他改了列卻永遠不生效。同步結果 toast 只報新增/更新/刪除，「跳過了幾張」被直接丟掉；體檢也沒有這一項。唯一線索是卡片上一顆沒解釋的小鎖 icon。

**建議修法**：只有「本次沒有任何保留/略過決定」才推進 appliedContentHash；試算表也存 appliedContentHash 並在來源頁常駐顯示「N 張卡已鎖定不受表格更新」＋一顆解鎖鍵；套用前對「全部保留的修改項」跳一次確認，講明「網頁的新內容會被丟棄」。

**證據**：`resync-apply.post.ts:238-255`（appliedContentHash 無條件寫入，與 decisions 無關——已實地確認）；`gsheet-sync.ts:99,170-176`；`ai-knowledge-chunks.ts:176-178`（manualEdit:false 不清旗標，gsheet 路徑沒有任何清除點）；`sources/index.vue:2745`（toast 丟掉 kept）。

### P0-5 匯入、OCR、切卡、自動套用燒 LLM 錢完全沒有上限，也沒有任何燈會亮

**會發生什麼**：整個系統唯一的額度閘門在「回答客人」那條路上。匯入 30 份掃描 PDF（OCR 每頁最貴）、整站匯入 50 頁、20 個常變的網址開自動套用——全部不受任何額度限制,「本期 AI 回覆 12/500 則」的進度條照樣一片綠。額度警示燈也只看回答數,import 桶完全不在覆蓋範圍。付費帳號連 token 護欄都不會讀。另外「小改自動套用」是**先花一次完整重切卡的錢、才判斷能不能自動套用**——常改版的頁面每次都付錢然後 100% 退人工,還沒有「連續 N 次都白花就別再試」的記憶。

**建議修法**：`recordAiUsage` 寫入後比對 import＋embedding 桶對月上限,80% 走既有的額度警告、100% 讓匯入/自動套用/建議掃描直接早退；來源上記「連續退人工次數」,連 3 次就跳過 LLM 直接標「有變動」。

**證據**：`ai-answer.ts:1404-1414`（全 repo 唯一閘門）；`ai-usage.ts:143-144,166-170`；`workspace-alerts.ts:582,643,654`（額度燈只看 answered）；`ai-knowledge-autoapply.ts:157-189`（先 LLM 後判定）＋`:26-29`（註解自承小來源必白花）。

### P0-6 匯入 job 的三個韌性缺陷：重收費、白作廢、殭屍來源

**會發生什麼**：

1. **租約 45 秒短於單步實際耗時**：一批 OCR 註解自己寫「15–25 秒」,Gemini 尖峰跑 50 秒很正常。租約到期 → 前端下一次輪詢立刻搶到 → **同 5 頁再 OCR 一次（重複收費）**。更糟的是進度存檔沒有版本鎖,兩個執行體交錯寫回會讓游標倒退,已付費切好的段整批消失重跑,token 還會重複入帳。
2. **一次暫時錯誤就終局作廢**：120 頁文件切到第 11 段時 Gemini 回一次 429 → job 被永久標 error（error 是終局狀態,永不再推進）→ 前 10 段已付的錢全作廢,只能整份重傳重跑。設計只防了閘道逾時,沒防上游 429/5xx。
3. **bulk-create 殭屍來源**：先建來源文件（宣稱 150 條、狀態正常）再逐卡建卡,中途 Lambda 死掉 → 留下「說有 150 條、實際 30 條」的來源;前端 catch 只 toast,使用者再按一次 → 第二個來源＋整批重複卡＋二次 embedding 費。沒有冪等鍵。
4. 附帶：**沒有取消端點、也沒有伺服器端推進器**——「背景工作」唯一的推進器是使用者開著的那個瀏覽器分頁,筆電休眠 job 就停在半路,一小時後被清掉,已付的 OCR 錢作廢。

**建議修法**：每步結束前續租（或租約拉到大於單步最壞值）＋進度存檔帶 `ifGenerationMatch`；catch 分類——429/5xx 只清租約讓下輪重接,連續 N 次才落 error；bulk-create 拿 jobId 當冪等鍵（jobId 即 sourceId）,chunkCount 建完才回寫實數;加 DELETE 取消端點,並把「撿起沒人推的 job 推一步」掛進 cron。

**證據**：`ai-preview-jobs.ts:53`（45s）、`:617-621`（saveWork 無版本鎖）；`preview-jobs/[jobId].get.ts:56`（不續租）、`:181-190`（一律終局 error）、`:49-50`（error 不再推進）；`bulk-create.post.ts:91-116,130-147`；`KnowledgeImportDialog.vue:1856-1859`；取消端點缺席：`preview-jobs/` 目錄只有 `[jobId].get.ts`。

## P1：近期要排

### P1-1 「貼上文字」匯入的卡全部變成無主卡，使用者填的產品名被靜默丟棄

貼文字匯入時,畫面上有「所屬產品」欄位、系統還花一次 LLM 幫忙預填,但後端建卡分支根本不含 text 類型 → sourceId 恆為 null、產品名從未寫入任何地方。結果就是 7/31 稽核與 `C-36` 反覆確認過會咬人的「無主卡」：客人指名問別台時被拿去混答,而且這批卡不屬於任何來源、無法重新同步、無法整批刪。修法＝text 也建 manual 型來源（手寫單卡那條路早就這樣做了,照抄即可）。
證據：`bulk-create.post.ts:65-67,89,120` vs `create.post.ts:19,46-69`；前端 `KnowledgeImportDialog.vue:335-347`。

### P1-2 排程掃描有 250 筆跨租戶天花板，超出的來源永遠輪不到、永遠不出聲

候選查詢「不等式＋limit(250)、無租戶過濾、無排序游標」→ Firestore 隱含按 refreshIntervalMinutes 升冪 → **每輪永遠拿同一批**,試算表（60 分）永遠排在網址（1440 分）前面。任一租戶接個 260 張表,其他租戶的網址偵測就整批停擺,來源頁照樣顯示「正常」。三個放大器：關掉自動同步的表仍佔名額（早退不戳 lastFetchedAt,永遠「到期」）;壞掉的來源無退避（權限被收回的表每小時打一次 API 打到永遠,穩佔前排）;run-tasks 無整體時間預算,一輪跑超過閘道 30 秒就 504 → 心跳沒寫 → 「背景維護停擺」誤報,實際每輪都跑了一半、部分工作還會重複執行。
修法：候選改「每租戶配額＋lastCheckedAt 游標輪轉」,撞上限回報 truncated;失敗來源升冪退避（interval×2^n,封頂 24h）;autoApply=false 在查詢層排除;心跳提前或給每任務 20 秒上限。
證據：`cron-maintenance.ts:364-381`（已實地抽查確認）、`:91,104-106`（早退不戳時間戳）、`:339-347,376-379`（無退避）;`run-tasks.post.ts:64,77`。

### P1-3 防重複來源的三道門全是「查不到＝沒有」的兩態

2. 同名來源偵測查詢失敗回空陣列,畫面顯示「沒有同名資料」,與真的沒有無法區分。

### P1-5 總覽卡失真家族

1. 子卡刪光後總覽卡留著,繼續對客人唸已下架的品項——而且它走較寬鬆的回答門檻,更容易被選中。`resync-apply.post.ts:56-59`
2. 手編過的總覽卡永遠不再更新,也沒有任何解鎖路徑（它被排除在 diff 之外,清鎖那條路碰不到它）——而它正是「你們有賣什麼」的唯一入口。
3. 重生總覽時把停用/過期/失敗的子卡也算進去 → 總覽說得出、細節卡查不到,AI 前後矛盾。`resync-apply.post.ts:33-51`
4. 試算表型錄沒有總覽重生,永遠停在第一次匯入的版本。
修法：子卡<2 時刪或停用總覽卡;UI 給「重新產生總覽」動作;childCards 過濾 status;gsheet 有增刪時呼叫同一支重生。

### P1-6 失敗可見性三缺口

1. 「自動偵測失效」（每輪抓到的內容都不同,系統標了 detectStalledAt）只有點進知識庫頁才看得到,小幫手與每日摘要都沒接——這正是 MYFEEL 首頁那種頁面必然落入的狀態。
2. 手動「重新同步」失敗不落地（不寫 failureReason/checkFailCount）→ 對「關了自動偵測」的來源連按五次失敗,列表照樣綠色。`resync-jobs.post.ts:58-61`
3. 權限收回的偵測線整體是通的（422→累計→failed→紅燈）,唯一漏洞是 refreshInterval=0 的表永遠不被掃,壞了永遠不亮。
修法：加 knowledgeDetectStalled 警示＋摘要補一行;手動失敗也走 checkFailCount 那套。

### P1-7 網址抓取無 SSRF 防護、無回應大小上限;上傳簽名網址無大小上限

有 sources.write 權限的使用者貼 `http://169.254.169.254/...`（AWS 中繼資料）或內網位址,內容會被切成知識卡回顯;整站探索更是把內網連結圖攤開。抓取用 `res.text()` 整包進記憶體,一個超大回應就 OOM。上傳簽名網址沒帶大小限制,PUT 2GB 照收,下載進 Lambda 才炸,而且炸掉後那顆檔案永遠留在 bucket。多租戶 SaaS 要修。
修法：解析 DNS 封鎖私有/回環/link-local 網段（含每一跳 redirect）;streaming 超過 ~5MB 中止;簽名網址加 `x-goog-content-length-range`,download 前先查 metadata。
證據：`ai-source-extractors.ts:272-311`;`ai-site-discovery.ts:37-50`;`upload-url.post.ts:40-46`;`preview-jobs.post.ts:87,201`。

### P1-8 同步併發競態（低頻但發生就留永久殘局）

1. 手動「立即同步」與排程同輪撞上（兩邊都無鎖）→ 同標題卡各建一張;之後每次同步的比對 map 只認一張,**被遮住那張永遠不更新也不刪除**,一直參與檢索。`gsheet-sync.ts:78-81,129-137`
2. 兩人同時 resync 同一來源:後到者對已刪卡 update 失敗被吞,來源照樣記成功。
修法：同步/套用前用 transaction 認領來源（SLA 提醒那套現成);gsheet 刪除迴圈遍歷原始清單把同鍵多餘卡收掉。

## P2：技債與白花錢

1. **白花錢五處**：resync 對「未變」卡回填問法用逐字比較,LLM 問法換個順序整批白重算 embedding（且 client 直送未正規化）;套用時不管有沒有動任何卡都重生總覽（LLM＋embedding 各一次）;每日摘要每 10 分鐘先跑 6 個查詢再判斷「今天發過沒」——一天 143 輪白讀,最壞 17 萬次/天,跟 8/11 讀取費暴衝同款形狀;知識卡 list 端點用 offset() 分頁且無分頁時整包撈（目前無呼叫端,屬地雷）;大而字少的文字版 PDF 被誤判掃描檔,白跑整套 OCR。
   （`resync-apply.post.ts:150-164,229-232`;`cron-maintenance.ts:817-906`;`paginated-collection-list.ts:53-62`;`ai-source-extractors.ts:87`）
2. **驗證缺口**：validateChunkInput 只擋空標題/空內容/5000 字,title 與 tags 無上限;註解宣稱的「過短 placeholder」檢查實際不存在於任何寫入路徑;gsheet 路徑完全不跑驗證（空答案列會建出「標題＝內容」的卡）;embedding 輸入字串無截斷,5000 字卡≈7500 token 遠超模型 2048 上限,可能每次 400、5 次後永久 failed。
   （`ai-knowledge-chunks.ts:51-56,65-76`;`gsheet-sync.ts:127-155`）
3. **三把「標題正規化」的尺不一致**：切卡去重（只去空白）、resync（小寫＋全半形）、gsheet/preview（去空白＋小寫）各一套 → 「iPhone 保固」與「IPHONE保固」入庫成兩張,之後每次同步都被誤報 removed,或在 gsheet 永久凍結。修法＝normalizeForCompare 提到 shared 四處共用。
4. **內容級重複無防線**：批次內去重只認標題;跨來源重複只有「≥3 張才警告」不擋寫入。現成的 contentSimilarity 可在合併階段加一輪 ≥0.9 判定。（與 `C-40` 修法 (c) 同一件事）
5. **來源管理雜項**：刪來源用單一 batch,>498 張卡整批失敗永遠刪不掉;單卡刪除 increment 維護 chunkCount 會漂（刪除確認框「底下 N 條」因此說謊）;migrate-orphans 一次噴 200 個來源,撞爆 list 的 100 筆與型錄快取的 200 筆隱形上限,真來源在畫面上憑空消失;手寫卡刪除會連坐刪掉還有其他卡的 manual 來源（潛伏,主 UI 目前不會踩）。
6. **清理與 TTL**：preview-uploads/ 的孤兒上傳檔沒人清（取消一次留一顆,最大 10MB）;knowledgePreviewJobs 無 Firestore TTL（只有程式單點清理）;清理不看狀態會刪掉還在跑的 job;建議收件匣 pending 無上限,破 500 後去重失效會自我增生;重試佇列的 pending 有隊頭阻塞（空內容殭屍卡永遠排最前面,每天被白 embed 144 次,還把別租戶擠出去）。
   （`ai-preview-jobs.ts:669-683`;`ai-knowledge-suggest.ts:396-405,504-522`;`ai-knowledge-chunks.ts:548-576`）
7. **小項**：resync-apply 不清 pendingHash（數字型網址套用後多繞一輪）;cache/extracted 寫了沒人讀（註解還誤導）;產品名快取只在單一 Lambda 實例失效,「改名→立刻重建」可能整批算到舊名;新增產品名不會讓既有卡重新認領;編輯內容不重置 retryCount;gap-scan 註解說每輪 2 個實際 1 個。

## 確認健康的部分（這些設計是對的，別在修上面問題時弄壞）

- **變更偵測的核心**：雙指紋（含抹數字第二道）＋連兩輪確認＋數字漂移學習＋back-to-applied,六態涵蓋完整,純函式可測。輪播/計數器頁騙不過它。
