> **這是凍結的決策紀錄，不是狀態看板。** 狀態一律看 `docs/STATUS.md`（本案＝`D-43`）。
> 起因：老闆 08-30 問「有標籤要審核、有知識庫需要補的，是否也要在小幫手或頁面提醒上？
> 以及評估所有這類型的提醒，是否在介面上有提醒或可以直接做的按鈕」。
> 白話版 artifact：「等人處理的事」。方法＝四路並行掃碼（提醒系統全表／貼標鏈路／知識庫鏈路／全後台佇列盤點），
> 關鍵結論逐一對到檔案行號。

## 一句話結論

異常提醒系統（32 顆，見「異常提醒對照表」artifact）管的是「**壞掉的東西**」，這次問的是另一型——
「**排隊等人做決定的東西**」。全後台這型佇列共盤出 **26 條**，其中 **8 條完全零提醒**（純靠使用者自己想到才進去看）。
兩題的直接答案：

1. **標籤要審核 → 該補，而且是唯一「有完整採用／忽略動作、卻整個不在提醒系統裡」的佇列。**
   正式資料實測（08-30，唯讀）：收件匣已堆 **42 位客人／68 條建議，歷來只有 2 條被人做過決定**（見 `STATUS.md` `C-108`）。
   建議加一顆**建議級** alert 進小幫手（比照知識庫建議的待遇），**不上**側欄／頁面提醒帶（不動 08-26 拍板）。
2. **知識庫需要補 → 已經有了**（小幫手「可以更好」卡＋頁內收件匣＋每日 LINE 摘要一行），
   不用新開提醒；剩四個「有做但到不了人眼前」的缺口，修的是準度不是新通道。

## 兩種「標籤要審核」——先分清楚，因為只有一種有提醒

| | ①「這位客人該貼哪顆標籤」 | ②「你該建一顆新標籤」 |
|---|---|---|
| 資料 | `userTagSuggestions/{wid}_{lineUserId}`（一人一份，`pending[]`） | `tagDiscovery/{wid}`（全站一份，`pending[]` 上限 6） |
| 審核 UI | 好友頁抽屜／對話頁右側客人卡（`AdminCustomerCard.vue:90-121`，採用／忽略＋「看這段對話」） | 標籤頁第一屏卡片（`tags.vue:25-80`，建立並貼上／忽略／取消忽略） |
| 小幫手 | ❌ **沒有**（`workspace-alerts.ts` 全檔不碰 `userTagSuggestions`） | ✅ `tagDiscoverySuggestions`（建議級，「去看建議」→ 標籤頁） |
| 頁外提醒 | 只有**每週**洞察 LINE 一行（`weekly-insights.ts:91-96`，且整段全零就不發） | 小幫手卡 |
| 頁內露出 | 標籤頁「待審 N 位」＋好友頁待辦條＋列上橘章（`C-108`，**已 commit `2198c10` 未推上 myfeel**） | 標籤頁卡片＋無建議時常駐細條 |

**①的積壓證明缺口是真的**：掃描器好好的（游標當天還在動）、13 顆標籤全是「先建議」模式，
但 68 條建議只有 2 條被決定過——不是功能壞，是**產出了沒有出口**。
`C-108` 的「待審 N 位」解決了「走進標籤頁的人」；這次評估補的是「**沒走進去的人要怎麼知道**」。

## 兩題的評估細節

### 題一：貼標建議待審，要不要上小幫手／頁面提醒？

**建議：上小幫手（建議級），不上頁面提醒帶。**

- **小幫手：加一顆 `tagSuggestionsPending`（建議級）**，落在「可以更好」組，跟 `knowledgeSuggestions` 同款待遇。
  - 探針：`count()` 或掃 `hasPending === true` 的文件數——索引 `(workspaceId, hasPending)` 現成（`C-108` 建的），
    比照 `knowledgeSuggestions` 探針（`workspace-alerts.ts:628-638`）一筆就亮、count＝人數。
  - CTA「去看建議」→ `/admin/{wid}/users?suggested=1`（深連結現成，`C-108` 加的）。
  - 無 fixOp、無劇本——採用前要看 60 字理由＋那場對話，一鍵全收＝盲簽（`D-34`／`ALERT-FIX-ACTIONS-EVAL-20260827.md:102` 歸類 C 的既有原則；`D-42` 也否決過整批審）。
  - 估工：探針＋前端註冊表一條＋測試，**約半天**。
- **頁面提醒帶：不加。** 08-26 拍板「建議級不上側欄／提醒帶」（`nav-alert-dot.ts:8-13`：常年都有的東西掛上去會變裝飾），
  且兩個相關頁面頁內已有露出（標籤頁「待審 N 位」、好友頁待辦條）——提醒帶疊上去是重複。**不建議翻案。**
- **每日 LINE 摘要：拍板題**（見下）。`knowledgeSuggestions` 在摘要有一行（`cron-maintenance.ts:1119-1121`，
  摘要自己查、不走 alert 管線）；貼標可比照加「N 位客人的標籤建議等你決定」。
  合規性 OK（`D-36` 拍板＝只搭已要發的摘要、不單獨觸發），代價是摘要再長一行。
- **最快的止血其實是推版**：`C-108` 的「待審 N 位」＋好友頁待辦條都還沒上線。先推、先讓 68 條有頁內出口，再補小幫手。

### 題二：知識庫要補，要不要上小幫手／頁面提醒？

**已經有了，不用新開通道。** 現況三條路：
① 小幫手「可以更好」卡（`knowledgeSuggestions`，1 筆 pending 就亮，count＝筆數）
② 知識庫頁內收件匣＋「N 件要處理、M 個 AI 建議」入口（`sources/index.vue:44-52`）
③ 每日 LINE 摘要一行點名最常問主題（`cron-maintenance.ts:1119-1121`）。
另外「AI 答錯了」那條是紅級、四面全亮＋LINE 即時推播，追得很緊，不在此列。

**剩四個實際缺口（修準度，不是開新通道）：**

1. **小幫手 CTA 落地沒有定位**：「去看建議」只帶到 `/knowledge/sources` 不帶參數（`useWorkspaceAlerts.ts:484-492`），
   落地後收件匣在「要處理的事」下方，要往下捲、沒高亮。→ 帶個 query（如 `?suggest=1`）自動捲到／展開，估半小時～1 小時。
2. **收件匣會消失**：它只掛在 `#editor-empty`（`sources/index.vue:318`）——點選任何一份資料整個收件匣就不見，
   只剩側欄一行小字；而且用 `?sourceId=`／`?q=` 深連結進頁時元件沒掛載、`suggestCount` 恆 0，**連那行小字的「M 個 AI 建議」都不顯示**（`sources/index.vue:2311-2317` 依賴 `@count` 事件）。→ 數字改由後端端點供給、不依賴元件掛載，估半天。
3. **FAB 上零訊號**：徽章只數紅級＋未完成必要設定（`TutorialAgent.vue:664`），開場白「我整理了 N 個建議」
   要 critical／warning／必要設定／加分項**全部清空**才輪得到（`:877-916`）——實務上等於永遠不講。
   → 低風險版：放寬開場白條件（有黃級時附帶提一句）；動 FAB 本體屬拍板題（見下）。
4. **AI 表現頁的「待補知識」工作台頁外零露出**：全站動作最齊的佇列（補知識／開對話／✓已處理／▶重演，
   `ai-usage.vue:221-310`），但沒有任何側欄點、小幫手卡、摘要提它——純靠使用者想到開 AI 表現頁。
   它跟 `knowledgeSuggestions` 是同一件事的上下游（沒補知識的轉真人案例 → 聚類成建議），
   收件匣看得到的人自然會回流，**暫可不動**；若要做，等 `C-6`（補卡成效回饋）一起。

## 「可以直接做的按鈕」評估

- **做得好的範本**：知識庫「要處理的事」11 項全有按鈕（單筆直跳／多筆清單／`orphan` 甚至一鍵整理）；
  建議收件匣的採用是全站最完整的閉環；答錯標記「改卡即銷案」免第二真相。
- **刻意不做一鍵、維持帶路的**（既有拍板，本次不翻案）：三種「採用類」建議（知識草稿／貼標／新標籤）
  都要人看過內容才能負責任地按——一鍵全收＝盲簽。規模化的正解不是批次按鈕，
  是把準的標籤升級成「AI 判到直接貼」（per-tag 三段，`D-27`），靠 09-20 的成效欄拍。
- **帶路可以更準的**：`knowledgeSuggestions` CTA 落地無定位（缺口 1）；貼標新 alert 的 CTA 直達 `?suggested=1`。
