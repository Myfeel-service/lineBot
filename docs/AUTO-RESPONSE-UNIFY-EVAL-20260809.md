## 結論先講

**應該合，但不是「把自動回覆搬進腳本編輯器」。**

直覺的做法是把自動回覆刪掉、全部改用腳本。這會壞事：**大多數需求就是一句話**，而腳本編輯器要人先理解「步驟、接線、流程圖」。真這樣做，最常見的需求會從「填兩格」變成「學會一個流程圖工具」。

正確的方向是 **一種東西、兩種深度**：新增時不問你要哪一種，先給最簡單的表單；需要多做一步時，同一筆設定就地長出流程。

> **複雜度是「答案」的屬性，不是使用者要先做的分類。**

---

## 一、為什麼現在這樣不夠好

上一輪已經把兩者收成一頁兩分頁、加了互相點名與蓋台警告。那解決了「怎麼選」，**沒有解決「必須先選」**。剩下三個代價：

### 代價 1：使用者要先做一個他做不到的分類決定

他心裡想的是「客人問運費就回一句」或「客人要查訂單，得先問編號」。他不會想「我需要一個狀態機」。要求他在動手前先把需求歸類到「自動回覆」或「客服腳本」，是要他用我們的內部架構來描述他的問題。

分頁標籤改成「一句話回覆／多步驟流程」讓這個決定變好做了——但決定本身還在。

### 代價 2：選錯了沒有回頭路

這是最貴的一個。規則長大是常態：本來「客人問退貨就回一句」，後來想「先問訂單編號再轉真人」。

現在的下場是**整條在另一個地方重做**。舊規則要記得停用（忘了就變成蓋台，而且不會有人告訴你——這正是 8/7 那次複讀災情的形狀）。

### 代價 3：順位陷阱是這個結構長出來的，不是 bug

兩套獨立的東西比對同一句話，就一定要有先後。實際順序是：

```
敏感情境 → 進行中的腳本 → 自動回覆 → 啟動新腳本 → AI
                            ↑ 永遠贏
```

我們現在是用「存檔前警告」去補。但只要是兩套，就永遠補不完——**合併成一個集合、用同一個優先度排序，這個陷阱會自己消失**。這是合併最大的實質收益，不只是介面比較整齊。

## 二、兩邊實際差多少（合併的工作量）

| | 自動回覆 | 客服腳本 |
|---|---|---|
| 關鍵字（含任一） | ✅ | ✅ |
| 含全部／完全一致／任何內容 | ✅ | ❌ |
| 看意思（語意） | ❌ | ✅ |
| 回一句話 | ✅ | ✅ |
| 貼標 | ✅ | ✅ |
| 開網址 | ✅ | ❌ |
| 觸發機器人模組 | ✅ | ❌ |
| 冷卻時間 | ✅ | ❌ |
| 問客人資料／記住答案 | ❌ | ✅ |
| 按鈕分路／依答案分路 | ❌ | ✅ |
| 存進客人資料 | ❌ | ✅ |
| 轉真人 | ❌ | ✅ |

**自動回覆本質上就是一條「觸發 → 回覆」兩個節點的腳本。** 差別不在「種類」，在「有幾步」。

要合併，**腳本要補五項**（不是三項——觸發比對那三種常被漏掉）：

1. 動作：開網址
2. 動作：觸發機器人模組
3. 冷卻時間
4. 觸發比對：含全部／完全一致／任何內容
5. 「只有一步」時的簡化外殼（不出現流程圖與步驟卡）

反過來，合併是有紅利的：**自動回覆也會拿到「看意思」的語意觸發**，那是它現在沒有、但很有用的能力。

## 三、建議的設定方式

### 新增時不問種類

```
┌── 新增自動回應 ─────────────────────────┐
│                                          │
│  客人說什麼      [ 退貨、退換貨、要退  ] │
│  比對方式        [ 含任一關鍵字      ▾ ] │
│                                          │
│  回什麼          [ 好的，請提供訂單編號 ]│
│                  □ 回完轉真人            │
│                  □ 同時貼標籤            │
│                                          │
│  ＋ 還要多做一步…                        │  ← 點了才長出流程
│                                          │
└──────────────────────────────────────────┘
```

八成的需求到這裡就結束了，跟現在的自動回覆一樣簡單。

### 需要時就地長大

點「還要多做一步」才出現：問客人資料 / 給按鈕選 / 依答案分路 / 存進客人資料。一旦超過一步，才顯示流程圖與步驟卡——**一步的時候不該有流程圖**。

關鍵是：**同一筆設定原地長大，不用換地方重做**。這一條就解掉了代價 2。

### 列表只有一份

不再有兩個分頁。每一列標「一步」或「N 步」就夠了，那是屬性不是分類。

## 四、風險與要小心的地方

**⛔ 最大的風險是把簡單案例弄複雜。** 驗收標準應該是：建一條「關鍵字 → 回一句話」的設定，**點擊數與欄位數不可以比現在的自動回覆多**。做不到就不要合。

**anyText 要重新想。** 「攔截所有文字」現在是排在最前面的特例，合併成單一排序後它變成一條優先度最高的設定——語意變了，得重新確認行為。

**別一次搬兩個資料模型。** 舊 `autoReplies` 不需要當場遷移：新的都走新編輯器，舊資料唯讀＋一顆「轉成新格式」。全部轉完再收掉舊集合。

**執行順位要一起改。** 合併的收益就在這裡：`handler.ts` 那條五段式編排要收成「敏感情境 → 進行中的流程 → 依優先度啟動 → AI」。這是動到 webhook 熱路徑，要有測試。

## 六、我的建議

**方向對，值得做，但這是「重寫一個功能」的量級，不是一輪 UX 修。**

而且**前提是這一輪的分頁先實際用過**。如果分頁＋蓋台警告就已經讓你不再困惑，那合併剩下的實質收益主要是「消除順位陷阱」——那可以用更小的方式先處理（例如把兩者的排序合成一張看得見的表，不動資料結構）。

### ✅ A 階段：簡單模式

`isSimpleMode` = 節點剛好是「觸發＋回覆」兩顆。命中時隱藏流程圖、步驟徽章、用途說明、`↳ 下一步` 接線提示與積木選單，兩張步驟卡退成 **「客人說什麼」／「你回什麼」** 兩個表單分節，底下只留一顆 `＋ 還要多做一步…`。

- 判定用**節點數**而不是讓使用者先選種類——複雜度是答案的屬性，不是分類。
- `blankForm()` 本來就產出觸發＋回覆兩顆，所以**新增時預設就落在簡單模式**，不需要另一條建立路徑。
- 加了第三步 → 同一筆設定就地長成完整編輯器，**不用換地方重做**（解掉報告裡的「代價 2」）。

**驗收標準達成**：建一條「關鍵字 → 回一句話」，腳本這邊是 名稱／關鍵字／回覆文字 三格；自動回覆是 名稱／關鍵字／回覆文字 **再加一步**（動作類型預設是「觸發機器人模組」，一定要手動改成「傳送文字」）。腳本反而少一步。

### ✅ B 階段第 1 項：三種比對方式

`ScriptTriggerNode.keywordMatch: 'any' | 'all' | 'exact' | 'anyText'`（省略＝`any`，舊腳本行為不變）。

- ⛔ 實作時發現 `matchesScriptTrigger` 與 `matchesScriptKeywords` **兩支比對函式並存**，而**只有後者真的在跑**（handler.ts:2732、playground.post.ts:38）；前者只剩測試在用。已把能力加在活的那一支、刪掉死的，並把測試改指過去——留著遲早會有人改到錯的那支、兩把尺開始分岔。
- `anyText` 沿用自動回覆同名選項的警告文案（會蓋掉 AI 與其他腳本）。
- `validateScriptDoc` 對 `anyText` 不再要求填關鍵字（那是自相矛盾的）。
- 新增 9 條測試（含「anyText 仍受停用擋住」「非 anyText 而關鍵字空白不可變成攔截全部」兩個危險邊界）。

### ✅ B 階段其餘三項：能力已對齊

**腳本現在做得到自動回覆的每一件事**，反之不成立。

| 能力 | 做法 |
|---|---|
| 開網址 | `ScriptReplyNode.linkUrl` / `linkLabel`（選填）。網址吃 `{{變數}}`，所以能把剛收到的訂單編號帶進查詢頁。獨立送一則 buttons template——**不塞進回覆文字那則**，那個 template 的 text 只有 160 字上限，回覆稍長就會被 LINE 整則退掉 |
| 觸發機器人模組 | 新節點型別 `module`（與 reply 一樣是終點，沒有 next） |
| 防重複觸發 | `ScriptTriggerNode.cooldownMs` ＋ 使用者文件上的 `scriptCooldowns`。冷卻中＝當作沒命中往下走（與自動回覆同語意，客人會由 AI 接手，不會沒人理） |

**⛔ 這一輪動到了正式的訊息發送路徑**，兩件事要特別記著：

1. **模組送出邏輯抽成 `replyWithFlowModule()`，自動回覆與腳本共用**。中間那段「這個模組其實是真人客服模組」的判斷（`resolveLiveAgentModuleReply` → `markWaitingAckSent` → `commitHandoff`）**絕不能有兩份**——分岔就會出現「客人按了真人卻沒真的轉真人」那種沒人看得出來的黑洞，這個專案踩過。抽取時 `preloaded` 傳的是 **Promise 不是結果**：先 await 再進去的話，「輸入中…」動畫會晚到預載之後才送。
2. **`hasScriptOutput()` 取代原本直接看 `result.replyText`** 的三處判斷。只附連結按鈕、或整則由模組出的步驟，`replyText` 都是空的但客人確實收到訊息了——用錯會讓機器人首接沒被記到（會話掛在「未首接」）、推進被誤判成「腳本壞掉」。

順帶修正的既有問題：**驗證器原本只認 `reply` 當終點**，`trigger → module` 這種完整設定會被誤判成「沒有路徑通到回覆」。已改成「回覆或機器人模組都算結尾」。

另外加了自動回覆沒有的把關：**連結網址沒有 `https://` 之類的 scheme 會在存檔時擋下來**（LINE 會在送出當下整則退掉，那是客人收不到、後台又看不出原因的失敗）。開頭是 `{{變數}}` 的放行。
