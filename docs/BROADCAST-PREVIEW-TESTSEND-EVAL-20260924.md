# 推播預覽畫的不是客人收到的東西＋沒有「試發一則」（2026-09-24）

> 決策紀錄，寫完凍結。狀態一律看 `STATUS.md`（`D-96`）。
> 老闆 2026-09-24 貼推播頁截圖：「推播預覽不應該長這樣吧，應該要呈現出使用者真實收到的樣貌，以及是否有測試推播的功能」。

## 一句話結論

**老闆是對的，而且比畫面難看嚴重得多**：選「觸發機器人模組」時，右邊畫的那張「點下面的按鈕看看／開始」卡片，**LINE 從來沒有送給任何一位客人過**。
送出端早在 **2026-05-07** 就改成「把那個模組裡的每一則訊息直接送出去」，客人手機上出現的是**圖文訊息＋一段文字**、不用按任何按鈕；而後台的預覽、單元測試、17 關守門員三邊都還停在舊的模型。
正式庫 43 則推播裡 **24 則是這一型**（56%），其中 **2 則還排程在 9/29 沒送**——現在打開那兩則，看到的都是錯的。

「測試推播」則是**完全沒有**這個功能。但 43 則裡有 **15 則是拿正式推播當試打用的**（名字帶「測試」或只送 1–3 人），老闆自己就建過兩則「匯入名單 1 筆」的——**功能不存在，需求已經被證實了 15 次**。

## 一、現在這張預覽，哪一條路是對的

| 店家選的動作 | 預覽畫出來的 | 客人實際收到的 | 對不對 |
|---|---|---|---|
| 傳送文字 | 一顆文字氣泡 | 一模一樣 | ✅ |
| 開啟網址 | 卡片＋一顆按鈕 | 一模一樣（網址會被換成追蹤轉址） | ✅ |
| **觸發機器人模組** | **卡片「點下面的按鈕看看」＋按鈕「開始」** | **那個模組裡的 1～5 則訊息，直接送到，不用按按鈕** | 🔴 **整張是假的** |

### 程式上是怎麼變成這樣的

- 預覽吃的是前端的 `unifiedActionToLineMessages()`（`shared/broadcast-content.ts:129-143`）→ 產出一張**按鈕範本卡**，按鈕帶 `postback: triggerModule=<模組 id>`。
- 但送出端（`server/utils/broadcast-send.ts:157-168`）會先認出那張卡是「觸發模組」型，然後：

  ```ts
  const triggerModuleId = extractTriggerModuleId(data.messages)
  let outboundMessages = data.messages
  if (triggerModuleId) {
    const rendered = await renderModuleToLineMessages(triggerModuleId, { … })
    outboundMessages = rendered.lineMessages as any[]   // ⚠️ 整張卡被丟掉
  }
  ```

  **那張卡連同店家寫的卡片文案、按鈕文字，一個字都沒有送出去。**

- 這段是 commit `5037c6a`（**2026-05-07**）加的；資料庫裡最早的推播是 2026-05-18。
  也就是說**沒有任何一位客人，透過推播收過那張卡**。

### 唯讀驗證（純函式，沒連任何服務）

把「預覽吃的那一份」與「送出端真正會做的判斷」擺在一起跑：

```
── 觸發機器人模組（店家有自己寫卡片文案）
  預覽畫出來的        : [{"type":"text","text":"中秋限定禮盒開賣了","buttons":[{"label":"看禮盒"}]}]
  送出端判到的模組 ID : mod_abc
  客人實際收到的      : 模組「mod_abc」的全部訊息（上面那張卡整張被丟掉）

── 開啟網址
  預覽畫出來的        : [{"type":"text","text":"點下面的按鈕看看","buttons":[{"label":"看詳情"}]}]
  送出端判到的模組 ID : (無→照 messages 原樣送)
  客人實際收到的      : 就是上面預覽那一則
```

## 二、影響範圍（myfeel 正式庫唯讀盤點，2026-09-24）

- `broadcasts` 共 **43 則**：**觸發模組 24 則**、純文字 19 則、開啟網址 **0 則**。
  → **預覽會說謊的那一型，正好是佔比最高的那一型**；而預覽唯一畫得對的「開啟網址」，這家店從來沒用過。

  → 預覽畫一張灰卡片，客人收到的是**整張大圖＋一段文案**。差距不是「樣式不夠像」，是**完全不同的東西**。
- **目前排程中、還沒送出去的有 2 則**（`電淨艙_開賣`、`小滑手_開賣`，都排 9/29 21:00）。現在點開它們，預覽畫的都是錯的。

## 三、跟著一起錯掉的四件事

### 1. 「卡片上要寫什麼／按鈕上要寫什麼」這兩格，對模組型是死的

`AdminAreaActionEditor.vue:248-251` 的 `actionSendsCard` 把 `uri` 與 `module` 都算成「會送出一張卡」，所以選模組時也會長出那兩格。
但模組型的送出端整張換掉——**店家在那兩格寫的字，沒有任何客人收得到**。這正是 `C-228` 當初要消滅的那種東西（「填了一個永遠不會出現的欄位」），只是換了個位置重演。

### 2. 單元測試與守門員，把錯的行為釘住了

- `shared/broadcast-content.card-copy.test.ts:165-178`：斷言模組型的預覽**必須**畫出「點下面的按鈕看看＋開始」。
- `scripts/broadcast-preview-check.mjs:250-261`：實機第 ④ 關同樣斷言那張卡。

兩邊都是全綠，而它們釘住的是一個**客人永遠收不到的畫面**。要修預覽，這兩處必須同時改成釘新行為——否則修對了反而變紅。

### 3. `F-9`「推播一次只送得出一則訊息」是錯的

`STATUS.md` 的 `F-9` 寫「所以推播做不到『一張圖＋一段文字＋一顆按鈕』」——**做得到，而且已經在做**：選模組時實際送出的就是圖＋文字兩則（模組上限 5 則，`flow.vue:1226`）。
畫面上那句「一則推播**只會送出一則訊息**」同理：對純文字／網址是對的，對模組型是錯的。
⚠️ `F-9` 的**結論**（要多則就去建模組）仍然成立，錯的是理由與畫面說法。

### 4. `D-87` 的主要理由，有一半在推播上不成立

`D-87` 當初的第一理由是「選觸發機器人模組時，客人收到『請點擊下方按鈕以進入機器人模組。』＋按鈕『開始』——後台自用的詞直接送到客人手機上」。
**在推播這條路上，那句話從來沒送到任何人手機上。**（那 24 則推播存的確實是那句話，但送出時整張被換掉。）
⚠️ `C-228` 本身沒有白做：自動回應／客服預存／活動那三條路是真的會送出去的，而且推播選「開啟網址」時也會送。只是「推播把術語送到客人眼前」這個**被當成頭號理由的事實**，是錯的。

## 四、順手挖到的兩顆地雷（與預覽同源，但比預覽嚴重）

### 🔴 地雷 A：模組被停用或刪掉，要到「按下發送」那一刻才會爆

- `getFlowByModuleId()`（`server/utils/handler.ts:810-822`）用 **doc id** 查，而且要求 `isActive`。
- 查不到或空的 → `broadcast-send.ts:164` 直接 `throw` → 整則推播標成 `failed`（受眾快照已經寫進去了）。
- **`POST /api/broadcast/[id]/validate` 完全沒有檢查這件事**：它只看「訊息不是空的」「狀態對不對」「受眾算得出人」。
  所以發送前的那個確認對話框會顯示「預估發送人數 842」，一切正常，按下去才失敗。
- 正式庫已經有一筆對不上的了：`MR測試`（2026-05-19）指向的模組 doc **現在查不到**。

排程推播踩到這個，爆的時間點是半夜排程跑的時候。

### 🔴 地雷 B：「我那天到底發了什麼」查不回來

- `broadcasts` 存的是**那張卡**，不是真正送出去的內容。
- 真正的內容在 `flows` 裡，而模組**隨時可以被編輯**，沒有版本。
- 所以：發完一個月後回頭看，後台畫給你的是一張沒送出去的卡，而真正送出去的那兩則早就被改掉了。
  `C-229` 檔頭寫的「已發送／已取消的推播也要看得到：那時人正在回頭查『我那天到底發了什麼』」——**這件事目前做不到**。

## 五、建議怎麼修

### P0-1　預覽改成畫「客人真的會收到的那幾則」（約 0.5 天）

做法已經現成，**不要另寫第二套**：`AdminActionPreview.vue`（`C-230`～`C-232` 做的）已經會「選了模組就去把那個模組真的抓回來畫」，而且是三態（還在抓／抓到了／抓不到）＋空模組攔截。推播只要接上同一套：

- 模組型 → 抓 `GET /api/flow/{id}` 畫真正的訊息（含圖文訊息 `richMessageRef` 的還原）。
- 預覽上方一句話講清楚**不用按按鈕**：「客人會直接收到這 2 則，不需要點任何東西」。
- 「抓不到」必須講（**不可以畫成空白**——那等於告訴他這個模組是空的，正是 `D-23` 害 667 人收不到歡迎訊息的形狀）。
- 純文字／開啟網址兩條路**原封不動**（它們現在是對的）。

### P0-2　模組型不要再問卡片文案（約 0.2 天）

`enableCardCopy` 改成只在 `uri` 時給那兩格，並在模組型時補一句「這則推播會直接送出模組裡的內容，不需要卡片文字」。
⛔ 已經存了卡片文案的那 24 則草稿不用清資料——送出端本來就不看它。

### P0-3　測試與守門員改成釘新行為（含在上面的工時裡）

- 單元測試：模組型改成斷言「預覽＝模組的訊息」，並**保留 uri 那條當對照組**（證明我們不是把整條路拆了）。
- `broadcast-preview-check.mjs` 第 ④ 關同理。
- ⭐ 破壞性驗證：把送出端的模組展開拿掉，這幾條要當場紅。

### P1-1　發送前就攔下「模組不見了／是空的」（約 0.3 天）

`validate.post.ts` 加一段：模組型就去確認那個模組存在、`isActive`、`messages` 不是空的。
講法要具體：「這則推播要送出的模組『乾淨方MAX＿超早鳥倒數』已經停用，現在發出去會整則失敗」。

### P1-2　送出時把真正送出去的內容快照回寫（約 0.3 天）

`broadcast-send.ts` 算出 `outboundMessages` 之後，連同 `sentAt` 一起寫回 broadcast doc（新欄位，例如 `sentMessages`）。
已發送的推播改讀這一份來畫預覽。**這是唯一能讓「我那天發了什麼」有答案的做法**——模組本身會被改。
⚠️ 舊的 24 則補不回來，不要假裝補得回來；那些就照現況標「當時的內容沒有留存」。

### P1-3　「試發一則給自己」（約 0.5 天）

- 新端點 `POST /api/broadcast/[id]/test-send`，body 給一個 LINE user id。
- **內容走跟正式發送完全同一條路**（`renderModuleToLineMessages` ＋ 追蹤連結包裝），這樣試發才有意義；⛔ 不可以另外組一份。
- ⛔ 不動 broadcast 狀態、不貼「發完的記號」、不寫成效報表、不佔 LINE 的彙總單位。
- 收件人怎麼挑：從「好友」清單挑一位（那頁本來就有「複製 ID」），記住上次用的那一個。
- 畫面上要講的三句：**這是真的會送到那支手機**、只送給這一位、跟正式發送內容一模一樣。
- 費用：我們這邊的「則數」額度算的是 **AI 回覆**（`shared/billing/plans.ts:31-41`），推播本來就不計，所以試發不吃店家額度；LINE 官方那邊每則照算（1 則）。

  ⚠️ **方案限制要一起想**：`planAllowsBroadcast` 把「非全體」的受眾全部歸類成 `advanced`，而輕量（399）與入門（799）是 `basic`。
  也就是說**那兩個方案的店家連現在的土法（標籤／匯入名單挑一個人）都走不到——他們沒有任何方式可以先試一發**。
  試發功能若也綁 advanced，等於把「別發錯」這件事做成加價功能。建議**試發不綁方案**（它本來就只送一則給自己）。
