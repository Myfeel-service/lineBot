# 全站權限設定盤點（2026-09-29）

> **決策紀錄，寫完即凍結。** 狀態一律看 `docs/STATUS.md`（`G-93`～`G-107`、`H-41`、`D-110`、`D-111`）。
> 老闆 2026-09-29：「檢查所有頁面所有功能的權限設定是否有怪怪的地方或是可以優化的地方」。

## 怎麼查的

- **只讀程式碼**，沒改程式、沒連正式庫、沒打線上 API。
- 分五路平行查：①對話與好友 ②推播、活動、模組、圖文選單、LINE、公開端點 ③AI、知識庫、小幫手 ④設定、成員、組織、帳務、超管、開帳 ⑤跨帳號（拿 A 家的權限動 B 家的資料）。
- 範圍：46 頁、275 支端點（`server/api` + `server/routes`），全部逐支列出它用哪一道門。
- 每一條 🔴 與 🟠 都回到原始碼對過一次，下面引用的行號就是當時看到的樣子。

## 一句話結論

**角色擋得住。** 觀察者沒有任何辦法寫資料，客服碰不到只有管理員能改的設定。
**真正的洞在「這筆資料是不是你家的」**：有幾支端點只看你是不是某個帳號的成員，卻不看你動的那筆資料屬於哪個帳號；另外兩支公開端點完全不用登入就能動到別家。
**另一個大問題是結構。** 權限表（`shared/permissions.ts`）號稱「單一事實來源」，但 275 支端點裡只有 34 支真的去讀它，其餘 177 支各自把角色寫死在程式裡。今天剛好大多對得上，已經有一處漂掉了（見 §2-3 最後一列）。

## 現在的權限怎麼運作

| 角色 | 叫法 | 大致能做的事 |
|---|---|---|
| viewer | 觀察者 | 只能看 |
| agent | 客服 | 回客人、維護內容（知識庫、自動回應、模組、推播、標籤……） |
| admin | 管理員 | 再加上設定（AI 設定、成員、LINE 憑證、帳單） |
| owner | 擁有者 | 目前跟管理員完全一樣（`D-7`） |

- **組織管理員**：對組織底下每個帳號都自動算管理員。
- **超管**：全部放行。
- **每一個動作要過兩層**：畫面上的顯示條件（側欄、頁面守門、按鈕 `v-if`），以及伺服器端的門檻（`requireWorkspaceAccess` / `requireCapability`）。
- **資料庫本身**：Firestore 與 Storage 的規則都是「全部拒絕」，前端不會直接讀寫資料庫，所以伺服器是唯一的門。

## 1. 會出事的（🔴）

### 1-1 A 家的客服可以換掉 B 家圖文選單的圖（`G-93`）

`server/api/richmenu/upload.post.ts:34-35`：

```ts
if (firestoreId) {
  await updateDoc('richmenus', firestoreId, { imageUrl })
```

- **漏在哪**：body 帶來的 `firestoreId` 前後都沒比對 `workspaceId`。同一組的 `setDefault.post.ts` 與 `[id].put.ts` 都有比對（`E-16` 修過），只有這支漏了。
- **怎麼被利用**：A 家的人先在自己帳號建一張選單，上傳圖片時把 `firestoreId` 換成 B 家某張選單的 id。
- **後果**：
  - B 家後台立刻顯示攻擊者的圖。
  - B 下次只要沒重傳圖就按存檔，`[id].put.ts:61-66` 會去抓那張圖、發佈到 B 的 LINE。B 的所有好友都會看到，圖可以做成假 QR 或假匯款資訊。
- **前提**：要知道 B 那張選單的 id（uuid）。離職成員、被移除的組織管理員手上就有。
- **修法**：在 `if (firestoreId)` 裡、上傳到 LINE 之前先讀文件，要求 `workspaceId` 與 `richMenuId` 都對得上，對不上回 404。

### 1-2 任何 LINE 使用者都能把自己塞進任一家的好友名單（`G-94`）

`server/api/liff/apply.post.ts:19` 與 `:30`：

```ts
const workspaceId = String(body?.workspaceId || '').trim()
...
await handleFollowEvent(lineUserId, { displayName, pictureUrl }, workspaceId)
```

- **漏在哪**：
  - 這支是活動頁的收尾。它只驗「這是一個真的 LINE 使用者」，不驗他是不是真的在這個帳號登記過活動。
  - token 是哪一個 LINE Login 頻道發的也不比對。`liff-token.ts` 的 `warnOnLiffChannelMismatch` 本來就只記 log，而這支連呼叫都沒有。
- **帳號 id 等於公開**：`/api/liff/claim` 會把 `workspaceId` 回給任何參加活動的人（`claim.post.ts:266`）。
- **後果**：
  - `handleFollowEvent` → `ensureUser` 會在 B 家建一位「好友」（名字、頭像由對方自訂），並開一場對話。
  - 換幾個 LINE 帳號就能灌一批假好友，污染 B 家的名單、統計、「全部好友」的推播對象。
  - 開帳「用手機測試」要找「剛加好友那位」時，也可能被搶先插隊。
  - 不會觸發歡迎腳本（沒有 replyToken）。
- **修法**：apply 只認 claim 當下簽發的短效憑證；或要求 `leadClaims` 裡真的有這個人、這個帳號、狀態是 claimed 的那一筆，帳號 id 直接從那筆讀，不收 body 帶的。

### 1-3 推播點擊轉址 `/api/r` 沒有簽章（`G-95`）

- **漏在哪**：
  - `server/utils/broadcast-click-track.ts:24-27`：token 只是把「推播 id｜｜｜連結代號｜目標網址」串起來轉 base64，沒有簽章。
  - `server/api/r/[token].get.ts:48` 只檢查網址是不是 `http` 開頭，`:76` 就直接轉過去。
- **後果（任何人都做得到，不用登入）**：
  1. **開放轉址**：可以組出「我們網域 `/api/r/…` → 任何網站」的連結，拿我們的網域做釣魚。
  2. **點擊數可以灌**：推播 id 就寫在每一條追蹤連結裡，拿到就能把那則推播的點擊數灌高，連帶影響推播報表與行銷月曆的數字。
  3. **沒有上限的寫入**：每打一次就寫一筆點擊紀錄，報表又會把它們全部讀出來。
- **修法**：照 `/api/t` 的做法，用各帳號的 channelSecret 做 HMAC 簽章並加到期時間；轉址前確認目標網址真的出現在那則推播裡。

### 1-4 被移除的組織管理員，仍然是他開的帳號的「擁有者」，而擁有者誰都拿不掉（`G-96`）

- **為什麼會卡住**：
  - 組織管理員在帳號選擇頁開新帳號時，會被寫成那個帳號的擁有者（`server/api/admin/org/[orgId]/workspaces/index.post.ts:68`，`role: 'owner'`）。
  - 把他從組織移除時，只刪組織名單那一筆（`org/[orgId]/members/[docId].delete.ts:57`），不會動他在各帳號裡的成員身分。
  - 擁有者不能被改角色、也不能被移除（`workspaces/[workspaceId]/members/[uid].delete.ts:23`、`[uid].put.ts:34`）。錯誤訊息叫人去「轉移所有權」，但全站沒有這個功能。
- **說法跟實際不一致**：組織頁移除前的確認文字寫「將失去這個組織底下所有官方帳號的管理權限」（`app/pages/admin/org/[orgId]/index.vue:703`），實際上不會。
- **後果**：離職的人照樣能看客人對話、改 LINE 金鑰、付款、邀人。要拿掉只能到 Firestore 主控台手動刪。這是 `D-7`（擁有者等於管理員、沒有專屬權限）在今天的具體後果。
- **修法**：
  1. 移除組織管理員時，一併處理他在該組織各帳號的成員身分。
  2. 補上「轉移擁有權」。
  3. 讓組織管理員與超管可以移除擁有者，並改掉那句確認文字。

### 1-5 「清除憑證」會刪掉整份帳號設定（`G-97`）

`server/api/admin/line-workspace/index.put.ts:64-66`：

```ts
if (body?.clearWorkspace === true) {
  await db.collection('workspaces').doc(wid).delete().catch(() => {})
```

- **現況**：
  - 畫面上的按鈕已經藏起來了（`organization.vue:360`，`showClearStoredCredentials = false`），但 API 還開著，前端呼叫的程式也還留著（`:728-748`）。
  - 按鈕文案寫的是「清掉本頁存的 Token／Secret」，實際做的是刪整份帳號文件。
- **一起被刪掉的**：
  - **方案**：帳號掉回免費。
  - **所屬組織**：組織管理員從此進不去，因為他們的權限是靠這份文件上的組織 id 查出來的；組織停用也擋不到這個帳號了。
  - **發票抬頭**。
- **修法**：只刪 `channelAccessToken`、`channelSecret` 這兩格（`FieldValue.delete()`），或整條路徑拿掉。

### 1-6 送出客服預存、貼標籤時，不看那個 id 是不是自己家的（`G-98`，衝擊低）

五個地方，都要先知道對方的 uuid（猜不到）才能利用：

- **送出客服預存**（`server/api/conversations/[userId]/send-preset.post.ts:35-36`）：只檢查預存存在不存在。隔壁的 `quick-reply-text.get.ts` 有比對帳號，所以這支是漏掉的。結果是 B 家的預存文字可以推到 A 家客人手上、存進 A 家對話紀錄，預存上設定的貼標也照單全貼。
- **貼標籤**（`users/[id]/tags.post.ts`、`user-tags/batch-add.post.ts`、`tagging.ts` 的 `addTagsToUser`）：收任意 tagId。好友頁讀標籤時（`users/list.get.ts:190`、`users/[id]/tags.get.ts:58`）也不比對帳號，會把 B 家標籤的名稱、顏色顯示出來。
- **建知識卡**（`ai/knowledge/create.post.ts:43`）：`sourceId` 不驗。卡片列表與回收桶會回傳 B 家來源的名稱，建索引時還會把 B 家來源的產品名抄進 A 家的卡。
- **模組引用圖文訊息**（`server/utils/handler.ts:1013-1020` 的 `loadRichMessageSnapshot`）：直接照 id 讀，不比對帳號。
- **建知識卡的 `folderId`**：不驗。填了不存在的資料夾，那份資料會從側欄消失。

**修法**：每一處都補一行「`doc.workspaceId === ctx.workspaceId`，不對回 404」，或把標籤過濾收進一個共用函式。

### 1-7 全站沒有一處檢查信箱是否驗證過（`G-99`，嚴重度看 Firebase 後台）

- **全站靠 email 認人**：組織管理員（`workspace-auth.ts:137`、`:331`）、邀請轉成員（`:339-341`）、帳號清單（`my.get.ts`）、自助開帳登記擁有者（`self-serve.post.ts:60`），全都只看登入 token 裡的 email。grep `email_verified` 零筆。
- **目前的防線**：登入頁只有 Google（`useAuth.ts:27-28`），而 Google 帳號的信箱一定驗證過。
- **危險在哪**：畫面上沒有「Email／密碼」擋不住人。只要 Firebase 後台開著 Email／密碼，或其他不驗信箱的登入方式，任何人都能拿公開的 apiKey 直接呼叫註冊 API，用「已被邀請、但本人還沒註冊」的信箱註冊，接管那個帳號或組織。
- **判斷**：
  - 後台實際開了哪些登入方式，這次**沒有查**（要連 Firebase 後台）。
  - 只開 Google：算「少一道防線」。
  - 開了 Email／密碼：就是 🔴。
- **修法**：統一取 email 的地方只在 `token.email_verified === true` 時才回 email，並去後台確認只開 Google。

## 2. 違反政策、或使用者會撞到的（🟠）

### 2-1 小幫手「上架／下架自動回應」跳過兩道檢查（`G-100`）

`server/utils/admin-ops.ts:413` 直接更新 `enabled`。同一件事在頁面上走 `ai/scripts/[scriptId].put.ts`，會多過兩道檢查：

- **方案閘門**（`:15`）：方案不含腳本功能的帳號，可以靠小幫手把腳本上架。
- **「加好友時」流程只能一條**（`:33-41`）：可以開出第二條，客人一加好友就連收兩份歡迎訊息。

**修法**：這個 op 的 preview 與 execute 補上同樣兩道檢查，或改成轉呼叫 PUT 端點（另外兩個 op 就是這樣做的，沒有問題）。

### 2-2 成員角色的三個洞（`G-101`）

1. **組織管理員同時是某帳號的直接成員時，拿到的是比較低的那個角色。**
   - `workspace-auth.ts:330` 只在「不是直接成員」時才看組織管理員身分，`my.get.ts:146` 也一樣。
   - 常見情況：先被邀成客服、後來才升組織管理員，他在那個帳號永遠是客服。
   - 也可以被故意利用：帳號管理員邀請一位組織管理員當觀察者，就能把他降級；成員列表還會把他「組織管理員」那一列藏起來（`members/index.get.ts:91`）。
2. **帳號層沒有「不能改自己、不能移除自己、不能移除最後一位管理員」的保護**（組織層有）。
   - 成員頁連自己那一列都有角色選單與移除鈕（`settings/members.vue:56`）。
   - 手滑把自己改成觀察者，會立刻被踢出設定頁。
3. **改角色、移除成員之後沒清權限快取**。只有邀請那支會清（`members/index.post.ts:114`）。被移除的人在同一台機器上最多還能再用 15 秒。

### 2-3 觀察者看得到按了會被拒的按鈕；客服看得到按了會失敗的修復鈕（`G-102`）

政策是「沒權限就直接藏起來」，以下幾處沒做到：

| 在哪 | 誰會撞到 | 按下去 |
|---|---|---|
| 對話統計頁的行銷月曆卡：「為這一檔擬推播」「這次不做」「還原」（`AdminMarketingCalendarCard.vue:102-142`） | 觀察者 | 403 |
| 同一張卡的「花 3 分鐘讓它認識」「去補主打商品」 | 觀察者、客服 | 被帶到開帳頁，看到「請管理員完成開通」 |
| 圖文選單整頁：新增、刪除、儲存、設為預設、AI 產生底圖（`richmenu.vue` 裡完全沒有角色判斷） | 觀察者 | 403 |
| 知識庫：從搜尋結果、體檢、疑似重複點進去，會打開完整的編輯視窗，裡面的儲存、刪除、AI 整理、重新學習都沒擋（`knowledge/sources/index.vue:3857`） | 觀察者 | 403 |
| 知識庫：資料拖曳、資料夾排序、卡片上的鎖頭、產品名稱整理、疑似重複的忽略與重掃、「一鍵整理」 | 觀察者 | 403，或按了沒反應 |
| AI 表現頁：「✓ 已處理」「補知識」（`ai-usage.vue:321`、`:325`） | 觀察者 | 403 |
| 異常提醒「按鈕沒反應」的「用聊天帶我修」（`useWorkspaceAlerts.ts:327` 開給客服，但 `broken-module-fix` 兩支都要管理員） | 客服 | 「查詢壞掉的按鈕失敗」 |

**最後一列就是 §5 講的「各自寫死」造成的漂移**：前端 08-28 照拍板改成客服看得到，後端端點沒跟著動。

### 2-4 「我接手」自動指派負責人從來沒生效（`H-41`，不是權限問題，順手查到）

- **錯在哪**：`server/api/conversations/sessions/[sessionId]/takeover.post.ts:64` 拿 `session.userId` 當對話文件的 id。但 session 存的是原始 LINE id（`conversation-session.ts:516`），對話文件的 id 是「帳號 id + LINE id」。
- **後果**：讀不到文件，指派這一步靜靜跳過，而錯誤又被 catch 吞掉（註解寫明「指派失敗不能讓接手失敗」）。
- **修法**：改用 `lineUserFirestoreDocId(session.userId, workspaceId)`，並比對帳號。

## 3. 補強（🟡）

### 3-1 只給超管看的欄位，API 沒擋（`G-103`）

畫面有藏，但 API 照樣回：

- **AI 設定 GET**（`ai/settings.get.ts`）：觀察者級，整包回傳，裡面有回答模型、embedding 模型、回覆長度上限、每月 token 上限，還有 LINE 通知名單。觀察者連 LINE 通知頁都進不去，卻拿得到名單。
- **小幫手 `get_ai_settings`**（`ai-admin-agent.ts:127-160`）：對觀察者回覆長度與 token 上限，跟 `get_ai_usage`「token 看不到」的說法互相矛盾。
- **轉真人清單**（`ai/usage/handoffs.get.ts:122`）：把外部服務的錯誤原文回給所有角色，畫面只在超管開「技術細節」時才顯示。
- **LINE 預警推播**（`ai-answer.ts:1624`）：沒有則數額度的帳號，推給店家的訊息會帶「本月 AI token 用量」。
- **開帳草稿 GET**（`knowledge-drafts.ts:109`）：會帶方案名稱給觀察者。

### 3-2 超管與快取（`G-104`）

- **超管沒帶帳號 id 時會變成全站範圍。** `workspace-auth.ts:310` 回空字串，不是回 400。
  - `server/utils/audience.ts` 用 `if (workspaceId)` 決定要不要加過濾，所以 `/api/audience/estimate` 會回全站人數。
  - `run-due-scheduled-broadcasts.ts` 同樣，`/api/broadcast/process-due` 會處理全站到期的推播。
  - 其他端點會寫出帳號 id 空白的孤兒文件，或直接 500。
  - 前端一律會帶，所以只有手打 API 才會碰到。
- **撤銷超管最長 1 小時才生效。** `verifyIdToken` 沒帶 `checkRevoked`，`super-admin.delete.ts` 只改 claims、沒有 `revokeRefreshTokens`。
- **「帳號 → 組織」的對應快取（60 秒）沒有清除函式。** 超管把帳號搬到別的組織後（`super/workspaces/[id].patch.ts`），舊組織的管理員最多還能用 60 秒。

### 3-3 公開、或只要登入就能打的端點（`G-105`）

- **`/api/onboarding/events`**：任何 Google 帳號都能打，一次 30 筆，沒有頻率限制，可以一直灌寫入費。
- **`/api/liff/lead-error`**：不用登入、不限次數寫入。
- **`/api/leads`**：「每個 IP 限次」讀的是客戶端可以偽造的 `X-Forwarded-For`，而且只在單一台機器的記憶體裡算。
- **`/api/liff/config?workspaceId=亂編`**：每個亂編的 id 會讀一次資料庫，並放進一份沒有上限的快取（`line-workspace-credentials.ts:19`）。

### `D-110` 客服可以做到哪裡？

今天這幾件都是客服就能做，伺服器也沒擋：

| # | 動作 | 影響多大 | 建議 |
|---|---|---|---|
| ① | 發推播給**全部好友**（也可以排程） | 全站影響面最大的一個動作 | 維持客服，但權限表要有「發送」這一項（見 §5）；要收到管理員，也做得到 |

政策只說「觀察者唯讀、不處理客人」，沒講個資與內部資料。今天觀察者看得到：

| # | 看得到什麼 | 建議 |

## 5. 結構：權限表名存實亡（`G-106`）

- **大多數端點沒讀權限表**：275 支端點裡，只有 34 支讀權限表（`requireCapability`），177 支直接寫死 `'agent'`／`'viewer'`／`'admin'`。
- **有定義、後端卻沒用**：`knowledge.write`、`broadcast.write`、`members.read`、`members.manage`、`line.manage`，後端一支都沒用。
- **表裡根本沒有**：對話、好友、標籤、客服預存、圖文選單、活動、模組、帳單，這幾類沒有對應的權限。
- **前端也是各寫各的**：大多用 `canOperate`／`canManageSettings`，少數頁面直接寫 `role === 'owner'`，只有知識庫與 AI 設定用 `can()`。

**今天為什麼還沒大出事**：兩邊剛好都對到同一級。但只要有人改一邊，另一邊不會跟著動，§2-3 最後一列就是這樣漂掉的。

**建議做法（一次做完，不要零星改）**：

1. **補齊權限表**：`conversations.reply`、`customers.write`、`tags.write`、`presets.write`、`marketing.write`（模組、活動、圖文選單）、`broadcast.send`、`billing.manage`。
2. **177 支端點全部改讀權限表**。純機械替換，行為不變。
3. **前端的 `canOperate`／`canManageSettings` 改成 `can('…')`**。
4. **加一支測試**：掃 `server/api/**`，只要有端點直接寫角色字串就紅燈。不然三個月後又長回來。

## 6. 查過、沒問題的

- **觀察者寫不了任何東西**：觀察者能打的端點全部唯讀，逐支看過。觀察者開頁時自動打的查詢也全是觀察者級，頁面不會因此壞掉。
- **沒有「換帳號」的洞**：沒有任何端點在守門之後，又去讀 body 或網址裡的帳號 id。全部用守門驗過的那一個。
- **帶 id 的端點幾乎都有驗歸屬**：知識卡、來源、資料夾、腳本、推播、活動、模組、圖文訊息、客服預存、標籤、對話、好友、會話、匯入工作、建議、草稿都有（例外就是 §1-1、§1-6、§1-2）。批次操作是逐筆驗。
- **小幫手不能被拿來越權**：提議與確認兩次都用呼叫者的角色比對；轉呼叫的端點會再驗一次；觀察者沒有任何工具做得到他自己做不到的事。
- **一鍵修的門檻**：每一個修復動作都跟「直接去改」的那支端點同級。
- **超管端點**：27 支都在第一行擋；超管頁面沒有去打一般端點撈全部租戶；不能撤自己、也不能撤最後一位。
- **組織**：看不到別的組織；移除組織管理員在 transaction 裡做，擋最後一位、擋自己；組織停用後，守門、帳號清單、組織端點三處都擋。
- **角色邊界**：管理員給不出、也改不成擁有者；客服在 LINE 通知頁只動得到自己那一列。
- **金流回呼**：PAYUNi 通知有驗簽（常數時間比對）、兩層成功判定、transaction 冪等、金額比對；導回頁沒有開放轉址。
- **LINE webhook**：用各帳號自己的 secret 驗簽，驗過的是哪個 secret 就歸哪個帳號。
- **公開連結**：`/api/t`、圖文訊息圖片網址有 HMAC 簽章加到期時間；`/c/:code` 只轉到 `/admin/`。
- **直傳 Storage**：簽名網址的路徑由伺服器組成、限定在自己帳號底下，只能寫、10 分鐘到期。
- **成本資訊**：`usage/summary` 逐欄位擋，AI 脈絡卡與測試對話的除錯資訊不含 token 或成本。
- **排程端點**：都要密鑰；沒設密鑰時退回「只准本機」，但線上一定經過 proxy（`x-forwarded-for` 必有），實際上走不到那條。
- **側欄與頁面守門一致**：觀察者看不到設定段，客服只看得到「LINE 通知」；直接輸入網址也會被同一套條件擋下。
