# STATUS.md → Notion 同步

把 `docs/STATUS.md` 的狀態推到 Notion「MiniMe 開發表」。**單向**：md 是上游，Notion 是展示層。用中文回覆（owner 用中文工作）。

## 這個 Skill 存在的原因

同步看起來只是「照編號比對」，但實際踩過的坑幾乎都不在比對本身，而在**開工前**與**寫入時**。以下每條規則都對應一次真實的錯誤。

---

## Step 0 — 開工前的四道關卡（不做完不要開始）

**① `git status` 必須乾淨。**
不乾淨代表有人正在動。踩過兩次：一次是 `.env.example`／`STATUS.md` 有未提交改動，去改會蓋掉別人的工作；一次是同步進行到一半 md 又進了 24 個 commit，剛建好的 `C-30` 十分鐘內就過期（它被修好了）。不乾淨時停下來問，不要自己判斷「應該沒差」。

**② 重新讀完整份 `STATUS.md`。**
不要靠記憶或稍早的讀取結果。長對話中上下文會被截斷，憑印象改檔會改錯行。用 `sed -n '1,70p'` 分段讀完，不要只讀有興趣的段落。

**③ 跑事實校對，把會漂的數字更新掉。**

```bash
wc -l server/utils/handler.ts      # E-2 與系統規格說明都引用
git rev-list --count HEAD          # STATUS.md 檔尾
```

檔尾的 commit 數幾乎每次都是舊的。

⛔ **要看推送狀態就指名 remote，不要用 `@{u}`。** 這個專案有兩個 remote，而 `main` 的 upstream 設的是 `origin`（`splashdigilab/linebot`），**但部署跟的是 `myfeel`**（`Myfeel-service/lineBot`）：

```bash
git rev-list --count myfeel/main..HEAD   # 這個才是「有沒有推上部署來源」
```

2026-08-28 那輪用了 `@{u}` 就誤報「98 個 commit 沒推」，實際上 `myfeel/main` 落後 0、全推上去了。`origin` 落後不影響任何事。

**④ 確認 `STATUS.md` 自己沒有內部矛盾。**
真的發生過：`E-6` 同時出現在技術債與完成區且說法相反；`B-3` 標 DONE 但其中半件根本沒做。發現矛盾先查證再同步，不要把矛盾原樣推去 Notion。

## Step 1 — 比對

**照編號比對，不要靠語意猜。** 兩邊命名刻意不同（md 寫「PAYUNi P3 每期續扣排程」、Notion 寫「每期自動續扣排程」）。編號是唯一對齊鍵。

```sql
SELECT url, "編號", "需求項目", "狀態", "模組", "優先級", "備註"
FROM "collection://82f6f257-a98b-4d2a-9ef9-b83f6423cd79"
ORDER BY "編號"
```

結果會分頁，用 `WHERE "編號" > 'X'` 取後半段。產出三張清單：**狀態不符**、**Notion 缺**、**Notion 有但 md 沒有**。

## Step 2 — 寫入

**只建還活著的項目**（`TODO`／`DOING`／`BLOCKED`／`DECIDE`／`DEPLOY?`）。已完成的不補卡——那是 git log 的工作，不是看板的。除非 owner 另外指定。

| md | Notion 狀態 |
|---|---|
| `TODO` | 尚未開始 |
| `DOING` | 進行中 |
| `DONE` | 已完成（填完成日期） |
| `DEPLOY?` | 推上正式站中 |
| `BLOCKED` | 等外部回覆 |
| `DECIDE` | 尚未開始 ＋ 需求類型標「內部決策」 |

F 區「已知限制」用「持續追蹤」，備註開頭加【已知限制】。

**⛔ 繁體字：長備註不要在工具參數裡逐字組 Unicode escape。**
這個錯犯了三次，其中一次是在「修正」前一次的同名錯誤時又打錯同一個字。錯出來的是日文異體字或形近字：`作廃`（應為作廢）、`精睈`（精靈）、`分攝`（分攤）、`要嘗`（要嘛）、`抽層`（抽屜）、`截断`（截斷）、`内`（內）。直接寫中文字元，寫完抽查標題欄。

## Step 3 — 一律回報、不自作主張

- **一對多編號**（`B-3a`／`B-3b` 這種後綴）：`CLAUDE.md` 說後綴只能當過渡。**逐組判斷，不要一刀切**——實際上三組答案不同：`B-4` 是 md 對（兩張講同一件事），`B-3` 與 `B-12` 是 Notion 對（md 漏拆）。
- **孤兒卡**（Notion 有、md 沒有）：標題看不出要解決什麼就去問人，不要自己編一個 md 條目。「登入對話方法」「整理 Omnichat 新增功能」掛了五天，就是因為沒人問。
- **md 與其他文件說法相反**：先查證程式碼，不要選一個看起來比較新的相信。
- **Notion 卡與已結案項目衝突**：⚠️ 不要急著駁回。踩過一次——「PAYUNi 申請書送件」看似與已結案的 `B-1` 矛盾，被我駁回；但上一輪同步的人是**刻意**不結案的，因為 `B-1` 只解決「幕後交易開通」，而「正式特店要不要送紙本」沒人能確定。駁回前先看子頁「MiniMe 的狀態記錄方式」有沒有記錄過這張卡的判斷。

## Step 4 — 不要從 commit 訊息推斷狀態

一定要回 `STATUS.md` 完成區對。從 commit 標題推「這張應該做完了」雖然猜對過，但那是運氣；commit 訊息只講做了什麼，不講剩下什麼。

## Step 5 — 子頁面

| 頁面 | 怎麼處理 |
|---|---|
| MiniMe 開發表 | 主要目標，見上 |
| MiniMe 的狀態記錄方式 | 同步日誌。每次同步都要更新「最後同步」那段 |
| MiniMe 系統規格說明 | 描述系統現況，程式改了就過期。校對重點：訊息流程（第三節）、13 個模組表（第四節，是 Notion 模組欄的來源）、規模數字（第二節）、上線阻塞（第七節） |
| 主管會議版（標題帶日期） | ⛔ 慣例是**開新版不改舊版**（旁邊已有「已取代・僅供追溯」）。動它之前先問 |

## 收尾（兩件都要做）

**① 更新父頁「MiniMe開發規畫表」頁首的「最後同步：YYYY-MM-DD」。**
這是夥伴唯一能自己判斷資料新不新的線索——看板停更時跟正常長得一模一樣，沒有紅字也沒有錯誤，就是安安靜靜地舊掉。2026-08-10 到 08-15 停了五天沒人發現，就是因為沒有這行。

**② 在「MiniMe 的狀態記錄方式」記下這輪做了什麼、以及還沒解的問題。**
那頁的價值在於下一個人不用重新發現同樣的坑。

⛔ 寫的時候不要在同一頁留兩段講同一件事的不同結論——舊結論要就地刪掉，要就劃掉並標明已被取代。真的踩過：該頁同時有「已解決」與「目前的缺口」兩段相反描述，舊的排在下面，導致一個早就定案的問題被連續三輪當成待決策事項丟給老闆。

## 已知的長期問題（每次同步都會遇到）

**上游只有一份，這件事已定案，不要再拿出來問。** `docs/STATUS.md` 是唯一事實來源：`TODO.md` 已於 2026-08-10 封存（`274480f`，16 個活項目併入並取得永久編號，對照表在該檔檔頭），`GOLIVE-BLOCKERS.md` 檔頭已聲明「狀態不看這裡」、只回答「缺什麼、去哪拿、為什麼要」。兩份自 08-10 後都未再變動。

⛔ 2026-08-15 曾把這個早就定案的問題連續三輪當待決策事項丟給老闆，根因是誤讀了 Notion 子頁裡排在後面的舊段落。**遇到「制度問題」類的描述先查檔案實況（`git log -1 -- <file>`＋看檔頭），不要相信文件裡的自述。**

**孤兒卡的真正來源是 Notion 端開卡，不是三份上游。** 四張都是有人直接在 Notion 建的。實務做法：編號為空 ＝ 還沒進 md，同步時一律收攏。角色分工見 Notion 的「🧭 誰能動什麼」頁。

**同步節奏與更新頻率不匹配。** `CLAUDE.md` 寫「一週一次」，但 md 一天更新好幾次。與其照日期，不如綁在「一批 commit 之後」。
