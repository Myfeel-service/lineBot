# 準度考卷（`C-297`）

拿真實客人問過的 66 題，問現在的 AI 客服（MYFEEL 的知識庫），量出五個數字：
**答對／答對一半／答錯／該答沒答／該轉沒轉**。之後改回答方式（例如 `C-298` 原文模式）時，同一份再考一次——
答對要變多、答錯不能變多、該轉沒轉不能變多，**三個都過才切換**。

## 怎麼考

```bash
EXAM_OUT=/tmp/exam/result.json \
  node --env-file=.env ./node_modules/vitest/vitest.mjs run --config scripts/kb-exam/vitest.config.ts
```

- 要用專案根目錄的 `.env`（有 Gemini 金鑰；`.env_myfeel` 沒有）。
- 結果寫到 `EXAM_OUT`（含客人原話與 AI 的回答，⛔ 放 repo 外面）。`summary` 是數字，`graded` 是每一題。
- vitest 會吞掉 console，看結果請看那份 JSON，不是看終端機。
- 只考幾題：`EXAM_ONLY=Q09,Q44`。同時問幾題：`EXAM_CONCURRENCY`（預設 3）。
- 出題輔助（看每題現在知識庫最像的 6 條）：`EXAM_MODE=evidence`，可另給 `EXAM_QUERIES=題目陣列.json`。

**花費**：真的打 AI，一題約 4～6 次呼叫（回答＋評分），整份台幣幾塊錢。⛔ 所以不在 `npx vitest run` 裡（那邊是每次改完都跑的單元測試）。

**正式庫零寫入**：讀 MYFEEL 的知識卡與設定；用量記帳換成什麼都不做；Firestore 所有寫入方法在這個程序裡直接丟錯，
開考前會先確認保險裝在回答流程用的那一個資料庫上。結果裡的 `blockedWrites` 應該是空的——不是空的＝回答流程多了一個寫入，要看是什麼。

## 題目與答案怎麼來

- 題目：2026-08-06～10-12 MYFEEL 真實對話裡的客人原話（AI 回合紀錄），去重後挑 66 題，分六類：
  該轉真人（要查他自己的訂單、要人處理）、價格、比較、一句好幾問、商品細節、規定（退貨、發票、付款）。
  只挑一句話自己看得懂的；個資拿掉（Q07 原文的姓名、電話、LINE、網址）。
- 每題的 `expect`：
  - `answer`：知識庫有答案，要答出來；
  - `handoff`：要查這位客人自己的訂單／帳號、或要人處理——該轉真人；
  - `clarify`：沒講是哪一台、答案又因產品而異——先問清楚是對的；每一台都答對也算對；
  - `either`：照要點答、或轉真人都可以（多半是知識庫沒有的題目：老實說不知道就對，編造就錯）。
- `kb`：出題當天知識庫裡有沒有答案。分開算才分得出「AI 沒用好現成的卡」跟「知識庫本來就沒有」。
- `keyPoints`（要講到的事實）、`mustNot`（出現就算錯）：照當天的知識卡與真人客服後來的回覆寫，⚠️ **還沒請客服看過**。
- 評分：AI 答了的題目由另一次 AI 呼叫照 `keyPoints`／`mustNot` 打分（`correct／partial／wrong`）；
  轉真人、反問則照 `expect` 直接判。規則在 `run.exam.ts` 的 `bucketOf` 與 `judge`。

## 什麼時候要改題目

- **知識庫改了**（出貨時間、保固、規格）：有時效的題目（例如 Q65 出貨時間）要點要跟著改，並更新 `keyPointsAsOf`。
- 評分員判得不對：先改要點的寫法（寫成「一定要講到的事實」，括號裡的補充會被當成必要）。
- 改了題目就把 `version` 加一；不同版本的分數不能直接比。

基準分數與第一次考找到的問題見 `docs/KB-EXAM-BASELINE-20261012.md`。
